# 04-需求分析：接到需求，以 Agent 视角进行分析和结构设计

> 当前笔记基于课件 PDF 整理；本课暂未提供视频转写。课件中可直接复用的原句、模板、话术已经融合到对应章节里，后续如果补充视频文字稿，可以继续增强“老师口播重点”和“原话话术”。

## 一句话主线

这一课解决的是：当别人丢给你一句很模糊的需求，比如“你看看怎么做个 AI 客服”，你不能直接进入功能设计，而要把它拆成一条可判断、可落地、可复盘的 AI 产品路径：

`需求分析 → 需求拆解 → 市场调研 → 竞品分析 → 产品设计 → 工作流`

对应到这节课的任务是：

`理解真实意图 → 结构化问题 → 判断值不值得做 → 找差异化 → 做 MVP → 结构和 Coze 落地`

最后形成 4 个产出物：

1. 需求结构图：目标、能力、知识、边界。
2. 调研结论 + 降本测算：确认值不值得做。
3. 差异化定位：明确切入点。
4. Coze 工作流：跑通基础 demo。

这节课最重要的总公式是：

> ==一句话拆解公式：目标（降本）→ 用户与场景（售后高频）→ 能力与知识（RAG + 接口）→ 边界（转人工）→ 落地（Coze）。==

## 1. 需求分析：不要停在“别人说出来的需求”

课件给出的原始需求是：

> “你们看咱们现在公司客服需求挺大，你看看怎么做。”

这句话表面上是在说“做一个 AI 客服”，但课程强调要拆出三层信息：

| 层级 | 含义 | 例子 |
|---|---|---|
| 说出来的 | 字面请求，通常已经是一个解决方案 | 做一个 AI 客服 |
| 真实目标 | 业务真正要达成的结果，才是衡量标准 | 降低客服人力成本 |
| 隐藏动机 | 个人或部门目标会影响方案接受度 | 今年 KPI 是降本增效 |

==所以需求分析的第一步不是“做功能”，而是确认：这件事真正要解决什么业务问题？谁来判断它成功？用什么指标判断？==

### 业务需求、用户需求、产品需求

AI 产品经理接需求时，要把需求从业务语言翻译成产品语言：

- 业务需求：公司或业务方想达成的目标，例如降低客服人力成本。
- 用户需求：用户希望被满足的体验，例如快速查到物流、退换货流程清楚、不重复描述。
- 产品需求：把业务和用户需求转成具体功能、流程、指标和边界。

链路是：

`业务需求 → 拆出用户需求 → 转成产品需求`

AI 客服比普通功能更复杂，因为普通功能偏确定性，而 AI 产品具有概率性、数据依赖和幻觉风险。课件强调 AI 客服需求分析必须看四件事：

- 数据：有没有知识库、历史工单、订单系统等“料”。
- 边界：什么情况绝对不能让 AI 自作主张。
- 衡量：上线后用什么指标证明价值。
- 迭代：上线后必须根据真实数据持续调参和补知识。

## 2. Agent 四问：目标、能力、知识、边界

课件要求记住四个词：

> 目标、能力、知识、边界。

这是从 Agent 视角拆需求的核心框架。

| Agent 四问 | 要回答的问题 | AI 客服例子 |
|---|---|---|
| 目标 Goal | 它必须达成什么结果？ | 不转人工解决 60% 售后咨询，降低人力成本 |
| 能力 Capability | 它必须会做什么？ | 意图识别、知识检索、订单查询、情绪安抚、转人工、多轮对话 |
| 知识 Context | 它靠什么回答？ | 退换货政策、商品文档、订单系统、历史工单 |
| 边界 Boundary | 它不能做什么？什么时候必须转人工？ | 投诉升级、退款审批、知识库没有、情绪激动 |

### 向不同角色问什么

需求澄清不是自己闷头想，要找不同角色问对问题：

- 问老板/业务方：这事成功的标准是什么？降本还是体验？
- 问客服负责人：最耗时、最重复的问题是什么？
- 问一线客服：哪些问题你们答得最累？哪些必须人来处理？
- 问用户：找客服时最烦什么？等太久？还是答非所问？

### 需求澄清 Checklist

接到一句模糊需求后，至少确认 8 件事：

| 维度 | 要问清楚什么 |
|---|---|
| 目标 | 最终目的是什么？成功怎么衡量？ |
| 用户 | 主要给谁用？C 端用户、内部坐席，还是主管？ |
| 场景 | 什么入口、什么情况下使用？ |
| 范围 | 先覆盖哪些问题？哪些明确不做？ |
| 数据 | 有哪些现成知识/数据？质量如何？能用吗？ |
| 边界 | 哪些情况必须人工介入？红线在哪？ |
| 资源 | 预算、人力、上线时间？ |
| 衡量 | 上线后用什么指标判断好坏？ |

### 和老板对齐的原话模板

课件给了一段很适合直接背的话：

> “我理解咱们这次要做的，是用 AI 帮客服团队分担售后高频咨询，目标是降低人力成本；第一版先覆盖退换货和物流查询，投诉这类还是转人工；成功的标准是自助解决率达到 60%。我这样理解对吗？”

这段话的作用是：

- 拉齐理解偏差。
- 锁定第一版范围。
- 拉齐衡量标准。

这也是 AI 产品经理在工作里很关键的表达方式：==先复述目标，再讲范围和边界，最后确认指标。==

## 3. 5W2H：把一句话需求拆成 7 个维度

课程给出的需求拆解路径是：

`一句话需求 → 5W2H 提问 → Agent 四问 → 需求结构图`

5W2H 是任何需求都可以先问一遍的基础框架：

| 维度 | 含义 | AI 客服例子 |
|---|---|---|
| Why | 为什么做：目的、价值 | 降低客服人力成本，同时不降低用户体验 |
| Who | 为谁做：用户、对象 | 主用户是 C 端售后用户，辅用户是客服坐席 |
| What | 做什么：范围、内容 | 先做退换货政策、物流查询、订单状态 |
| When | 何时/何场景 | 下单后、发货后、收货后售后 |
| Where | 在哪用：渠道、入口 | 官网客服、App 客服、微信公众号 |
| How | 怎么做：形态、方式 | 对话式 AI，RAG + 订单 API，困难情况转人工 |
| How much | 投入多少：成本、资源 | 2-3 周第一版，你 + 1 名开发，现有工单和政策可用 |

这里最关键的是，==5W2H 不是填表，而是逼自己把“做什么、不做什么、怎么衡量”讲清楚。==

## 4. 目标要可量化：从“做好客服”到“自助解决 60%”

课程里把==目标澄清分成一个阶梯==：

1. 做好客服：太宽泛，无法衡量。
2. 让 AI 多处理一些问题：有方向，但没有数字。
3. AI 自助解决 60% 的售后咨询：有核心指标。
4. 进而人力成本下降约 30%：连接业务价值。

好目标要满足三点：

- 可衡量：有数字。
- 对齐业务：不是为了做 AI 而做 AI。
- 有边界：知道第一版先解决哪部分。

辅助指标包括：

- 首次响应时长。
- 转人工率。
- 用户满意度。

## 5. 能力与知识：AI 客服不是只靠大模型

用户问“我的订单到哪了”，==AI 客服真正要跑的是一条能力链==：

1. 意图识别：判断用户是在查物流。
2. 信息补全：追问订单号或手机号。
3. Function call / 接口调用：查询真实订单和物流状态。
4. RAG：检索物流问题解决方案或帮助中心条款。
5. Prompt 生成：组织成有温度、有风格的回复。

课件示例回复：

> “亲，现在您的物流已经到 xxx 了，可能存在驿站了，先看下短信通知吧。（根据帮助中心第五条建议）”

==知识来源主要有四类==：

| 知识来源 | 用途 | 注意点 |
|---|---|---|
| 退换货政策/公司规则 | 回答规则类问题 | 结构化、相对稳定 |
| 商品文档 | 回答材质、尺寸、保养、口味等 | 量大，需要整理 |
| 订单系统 | 查实时订单/物流状态 | 需要接口实时查 |
| 历史工单 | 挖高频问题、补充语料 | 可用于聚类和问答优化 |

## 6. 边界设计：什么时候必须转人工

AI 产品需求里，==“边界”不是附属项，而是安全底线。==

课件列出的转人工场景：

- 投诉升级：用户明确表达强烈不满、要投诉，人来处理更稳妥。
- 退款审批：涉及钱的决策，必须人工确认，AI 不能擅自答应。
- 超出知识范围：知识库没有、置信度低的问题，转人工而不是瞎编。
- 情绪激动：识别到用户愤怒或焦虑，优先转人工安抚。

核心原则：

> ==宁可多转人工，也不要让 AI 在高风险场景自作主张。目标是成本，但底线是质量。==

另一个很重要的金句：

> ==转人工不是失败，是负责任。让用户感到“答不了会有人接着帮我”，信任才建立得起来。==

### 置信度和情绪识别

两个关键点：

| 关键点 | 怎么判断 |
|---|---|
| 置信度阈值 | 多有把握才让 AI 自己答？先保守设高，跑稳后再放宽 |
| 情绪识别 | 看关键词，如投诉、垃圾、退钱、差评；看语气强度、感叹号、重复表达 |

课程提醒：阈值太高会动不动转人工，省不了人；阈值太低会乱答错答，体验差。第一版建议保守，用真实数据不断校准。

## 7. 用户故事和任务流：每一步暴露能力与知识

用户故事示例：

> 作为消费者，我想查到薯片到哪了。

任务流：

`用户发问 → 识别意图 → 补全信息 → 调用接口 → 组织回复`

映射到例子：

`“我的薯片到哪了” → 查物流 → 追问订单号/手机号 → 查真实物流状态 → 告知状态 + 预计时间`

走任务流的好处是：==每一步都暴露出 AI 必须具备的能力和知识。== 比如“补全信息”这一步，就说明 AI 必须支持多轮对话，并能引导用户给订单号。

## 8. MoSCoW：圈定第一版 MVP

需求不可能一次做完，要先排优先级。

| 优先级 | AI 客服例子 |
|---|---|
| Must 必须做 | 物流查询、订单状态、退换货政策问答 |
| Should 应该做 | 常见商品咨询、发票问题 |
| Could 可以做 | 主动关怀、满意度回访 |
| Won't 暂不做 | 投诉处理、退款审批、营销推荐 |

课程的判断：

> 第一版 = Must。==把 Must 做扎实，比把 Could 做一半更有价值。==

第一版范围：

| 第一版做 | 第一版不做 |
|---|---|
| 物流查询（调订单接口） | 投诉处理与升级 |
| 订单状态查询 | 退款审批 |
| 退换货政策问答（RAG） | 商品营销推荐 |
| 低置信/情绪 → 转人工 | 多语言、语音 |

MVP 的判断标准：

> ==能不能跑通“问 → 答/查 → 答不了转人工”这个最小闭环。==

## 9. 一页纸需求文档：给老板看的第一份东西

课件说：

> ==把结构图浓缩成一页文字，这就是你给老板看的第一份东西。==

一页纸需求文档可以这样写：

| 模块 | 内容 |
|---|---|
| 项目名称 | 零食电商 · AI 售后客服（一期） |
| 背景/目标 | 客服人力成本上涨；用 AI 分担售后高频咨询，目标自助解决率 60%、人力成本 -30% |
| 目标用户 | C 端售后咨询用户（主）；客服坐席（辅） |
| 核心场景 | 物流查询、订单状态、退换货政策问答 |
| 关键能力 | 意图识别、RAG 检索、订单接口调用、转人工 |
| 第一期不做 | 投诉、退款审批、营销、语音/多语言 |
| 衡量指标 | 自助解决率、转人工率、满意度 |
| 资源/排期 | 你 + 1 开发；Coze 搭建；3 天出 Demo；2-3 周出可用版 |

## 10. 需求拆解常见 5 个错误

| 错误 | 后果 |
|---|---|
| 目标不可量化 | “做好客服”永远说不清做到没做到 |
| 范围无限扩张 | 什么都想做，第一版做不完、做不精 |
| 忽略知识来源 | 只想功能，没盘点有没有数据可喂 |
| 不设边界 | 让 AI 处理退款投诉，容易出事担责 |
| 不定衡量指标 | 上线后无法证明价值，没有后续支持 |

拆解结束后用 6 个问题自检：

- 目标有具体数字，能衡量成败。
- 用户对象明确，主用户和辅助用户都写清。
- 范围画定，知道先做什么、不做什么。
- 盘点了知识来源，确认有数据可用。
- 划清了转人工的边界与红线。
- 定义了上线后的衡量指标。

## 11. 市场调研：判断值不值得做

课件原话：

> ==需求拆得再漂亮，如果方向错了，也是白做。调研就是来纠偏的。==

调研要回答三件事：

| 问题 | 含义 |
|---|---|
| 需求是真的吗 | 老板觉得该做，但用户真有痛点吗？数据支持吗？ |
| 价值有多大 | 做出来到底能省多少、提升多少？值得投入吗？ |
| 做得出来吗 | 公司有没有数据和知识喂给 AI？技术上可行吗？ |

调研给产品经理三样东西：

- 做不做的底气。
- 怎么做的方向。
- 说服老板的证据。

### 三个调研方向

> ==用户告诉你“该不该做”，市场告诉你“值不值”，数据告诉你“能不能”。==

| 方向 | 看什么 | 决定什么 |
|---|---|---|
| 用户研究 | 谁在用客服、为什么来、最烦什么 | 做不做、先做哪些场景 |
| 市场研究 | 行业成本、AI 渗透率、增长趋势 | 估算价值、对标行业水平 |
| 数据可行性 | 公司有什么数据、够不够用、合不合规 | 能不能做、要补什么 |

### 从数据挖高频问题

方法：

`拉历史工单/聊天记录 → 聚类归类 → 按频次排序`

示例结果：

| 排名 | 问题类型 | 占比 |
|---|---:|---:|
| 1 | 我的订单/物流到哪了 | 22% |
| 2 | 怎么退货/换货 | 18% |
| 3 | 退换货政策是什么 | 12% |
| 4 | 商品口味/保质期咨询 | 10% |
| 5 | 发票怎么开 | 6% |
| 6 | 其他长尾 | 32% |

结论：

> ==前 3 类（物流 + 退换货）就占了 52% —— 做好它们，就解决了一半以上的咨询量。==

### 用户痛点语义分析

从差评、社媒吐槽、工单备注里提炼痛点：

- 等待太久：高峰期排队，等不及就走了。
- 重复描述：转接后要把问题再讲一遍。
- 答非所问：客服念模板，没真正解决问题。
- 下班没人：晚上和周末没人工，问题搁置。

AI 客服的天然优势是：

> 7×24 在线、零等待、不会不耐烦。

### 数据可行性

| 数据状态 | 例子 | 用途 |
|---|---|---|
| 有，且可用 | 历史工单、聊天记录 | 挖高频问题、做语料 |
| 有，需整理 | 退换货政策、商品文档 | 汇总成知识库 |
| 要打通 | 订单系统 | 实时查询 |
| 暂缺 | 标注好的优质问答对 | 边上线边积累 |

结论示例：

> 数据基础够支撑第一版 —— 先用现成的政策 + 订单接口起步，语料边跑边补。

### 调研输出：把调研变成能拍板的结论

调研结论要回答三句话：

- 值得做：售后高频咨询量大且集中，用户痛点明确，行业已成趋势。
- 这么做：先做物流 + 退换货（占 52%），RAG 知识库 + 订单接口起步。
- 有回报：预计自助解决 60%，人力成本下降约 30%，数据基础已具备。

课件总结：

> ==这事值得做、知道怎么做、能算出回报 —— 调研的使命就完成了。==

## 12. 运营主管访谈提纲

课件给出的访谈问题很适合直接复用：

1. 目前每天大概多少咨询量？分几个班次？
2. 最高频的问题是哪几类？各占多少？
3. 哪些问题最耗时、最让坐席头疼？
4. 哪些问题其实答案固定、完全可以自动化？
5. 哪些问题你绝对不放心交给机器？为什么？
6. 现在用户投诉/不满主要集中在哪？
7. 你们有沉淀好的标准话术或 FAQ 吗？
8. 如果有 AI 帮手，你最希望它先帮你做什么？

## 13. 竞品分析：不要抄功能，要找空位

==竞品分析的目的不是“看别人有什么我也做什么”，而是找到不一样的位置。==

| 误区：抄功能 | 正解：找空位 |
|---|---|
| 看对手有什么，我也做什么 | 看对手没做好什么、漏了什么 |
| 做成一个缩水版的它 | 找到我们能做得更好的点 |
| 在它擅长的地方硬碰硬 | 避开正面战场，打差异化 |
| 结果没特色、拼不过 | 结果窄而准，有立足点 |

课件对本项目的判断：

> ==不跟大厂拼“大而全”，要找一个零食电商能赢的“小而精”切口。==

### 三层竞品寻找

| 类型 | 含义 | 例子 |
|---|---|---|
| 直接竞品 | 同样做电商 AI 客服的方案 | 大厂智能客服平台、AI 客服 SaaS |
| 间接竞品 | 解决同一问题的其他方式 | 工单系统、人工客服外包、FAQ 自助页面 |
| 替代方案 | 用户或公司可能采用的土办法 | 继续纯人工、加派人手、电话热线 |

### 竞品对比维度

用四个维度拆：

- 功能。
- 体验。
- 技术路线。
- 成本。

对比大厂平台、垂直工具、自建方案：

| 维度 | 大厂平台 | 垂直工具 | 自建方案 |
|---|---|---|---|
| 功能覆盖 | 很全 | 够用 | 按需做 |
| 接入难度 | 较重 | 轻 | 中 |
| 定制灵活 | 弱 | 中 | 强 |
| 懂业务 | 弱 | 弱 | 强 |
| 成本 | 高 | 中 | 中低 |

我们的优势种子是：

> ==自建方案在“懂零食电商 + 灵活”上明显占优。==

### 实测体验

用核心高频问题去试竞品：

1. “我的订单到哪了”：能不能查真实物流，还是只给通用话术？
2. “怎么退货”：能不能讲清流程，还是甩链接让你自己看？
3. 故意答得含糊：会不会转人工？转得顺不顺？

### 差异化定位

课件给出的定位句：

> ==“不做大而全的通用客服，做零食电商售后的‘窄而准’专家 —— 把 Top 高频问题 + 真实订单查询做到又快又准，成本低、上线快。”==

可压缩成三个字：

- 准：深耕售后，答得比通用方案准。
- 快：聚焦高频 + 接订单，秒级真实回答。
- 省：接入轻、用现成平台，成本可控。

## 14. 产品设计：五层结构与五个要素

课件把 AI 产品结构拆成五层：

| 层级 | 角色 | 任务目标 |
|---|---|---|
| 用户层 | 产品经理、UI/UE | 良好的用户体验：简洁提问、拿到需要的答案、驱动动作结果 |
| 提示词/应用层 | 提示词工程师，AI 产品经理部分兼任 | 提示词结构化便于开发；提高回答确定性和可控性 |
| 应用能力层 | 研发主导，产品辅助 | RAG、Function call、MCP、接口调用、知识库导入和评测 |
| 模型层 | 大模型厂商、算法工程师 | 提升泛化能力或垂直能力，控制准确性、易用性和成本 |
| 数据层/算力层 | 数据方、客户、算法与芯片厂商 | 提供丰富可靠的数据湖，提升算法算力 |

==落到 AI 客服，需要五个要素==：

| 要素 | 内容 |
|---|---|
| 接入 | 官网、App、公众号、淘宝等入口 |
| 理解 | 意图识别、订单号提取 |
| 决策 | 路由：解答、查数据、转人工 |
| 能力 | RAG、订单接口、话术生成 |
| 兜底 | 转人工 |

### 理解：听懂用户到底想干什么

理解层做两件事：

- 意图识别：把用户的话归到预设意图，比如查物流/订单状态、退换货咨询、政策问答、商品咨询、投诉。
- 信息提取：从对话里抽出关键参数，比如订单号、手机号、商品名称、时间范围。

缺信息时，AI 要主动追问。

### 决策：这个问题走哪条路径

决策路由的规则：

> ==能用知识库答的优先答；涉及实时数据就查接口；拿不准就转人工。==

| 问题类型 | 路由 |
|---|---|
| 物流常识问题 | 走 RAG 检索知识库 |
| 要查实时数据 | 调订单/物流接口 |
| 高风险/答不了 | 转人工兜底 |

### 能力：具体干活的几个模块

第一版先搭四块：

- RAG 检索：从知识库找政策/商品答案，带出处。
- 订单接口：实时查物流、订单、退款进度。
- 话术生成：把结果组织成自然、有温度的回复。
- 转人工交接：打包上下文，顺畅转给坐席。

## 15. 用户对话流程与 Coze 节点映射

用户对话流程：

==用户提问 → 意图识别 + 提取信息 → 决策路由 → 调用能力（RAG/接口）→ 生成回复==

任意环节遇到低置信、情绪、越界，就转人工。

课件强调：

> 这条流程，就是下一模块在 Coze 里要搭出来的东西。

结构图与 Coze 节点的对应关系：

| 结构模块 | Coze 中的搭法 |
|---|---|
| 理解层（意图识别） | 意图识别节点 / LLM 节点 |
| 决策层（路由） | 条件分支（选择器）节点 |
| 能力层（RAG） | 知识库节点 |
| 能力层（查订单） | 插件 / API 节点 / 数据库 |
| 兜底层（转人工） | 转人工 / 消息节点 |

关键金句：

> ==设计图做得越清楚，这一步映射就越顺 —— 搭建只是“把想好的东西连起来”。==

### Coze 工作流课件要点

课件后半段从结构图切到对话流，展示了订单查询 demo 的基本逻辑：

1. 开始节点预留 `user_ID`，以后接入其他系统。
2. 意图识别节点分析用户输入，决定走不同分支。
3. 第一版先做隔离：如果不是查订单，都转人工。
4. 如果是查询订单，走上方路由。
5. 大模型组件从用户输入拆解内容，填充槽位。
6. 判断用户提供的是订单号还是手机号：
   - 有订单号：不需要其他输入。
   - 没有订单号但有手机号：可能能查，需要进一步逻辑。
   - 什么都没有：要找用户补充信息。
7. 选择器判断 `order_ID` 是否为空。
8. 查询插件（Function call）：输入订单号，返回订单查询结果。
9. 问答器在缺信息时向用户要信息。
10. 下一节继续解决手机号查询问题，因为一个手机号可能关联多个订单，需要数据库查询和循环。

## 16. PRD 描述要点与评估标准

PRD 要写清楚：

| 模块 | 内容 |
|---|---|
| 产品概述 | 零食电商 AI 售后客服一期，降本为目标 |
| 用户与场景 | C 端售后用户；物流、退换货高频场景 |
| 功能列表 | 意图识别、RAG 问答、订单查询、转人工 |
| 核心流程 | 提问 → 理解 → 决策 → 调能力 → 回复/转人工 |
| 数据与接口 | 知识库（政策/商品）+ 订单系统接口 |
| 边界与异常 | 投诉、退款、低置信、情绪 → 转人工 |
| 评估指标 | 自助解决率、转人工率、满意度 |
| 排期 | 知识库整理 1 周 + Coze 搭建 1-2 周 |

评估指标：

- 自助解决率：AI 独立解决的占比，目标 ≥ 60%。
- 转人工率：转给坐席的比例，越低越好，但不能牺牲质量。
- 首次响应时长：用户多久收到回复，目标是秒级。
- 用户满意度：对话后的评价/点赞，持续提升。

课件提醒：

> ==这几个指标，正好对应老板最初的“降本”目标 —— 闭环回到了第一页。==

## 17. 本课作业：入职助理

练习需求：

> “帮我们做一个 AI 助理，帮公司新员工解答入职相关问题。”

作业要交付 4 份产出物：

| 产出物 | 内容 |
|---|---|
| 需求结构图 | 目标/能力/知识/边界 + MVP 范围 |
| 调研结论 | 高频问题 + 可行性 + 价值判断 |
| 差异化定位 | 竞品对比 + 你的切入点 |
| Coze 工作流 | 搭一个能跑通的最初版 |

练习拆解方向：

- 5W2H：把入职助理填满七个维度。
- 定量目标：把目标写成带数字、可衡量的一句话。
- 能力与知识：它要会什么，靠哪些资料/系统回答。
- MoSCoW：圈定 MVP，先做 Must。
- 五层结构：接入/理解/决策/能力/兜底。
- 兜底与指标：什么情况转 HR，用什么指标衡量好坏。

## 18. 复习时要背下来的句子

1. 接需求时先追真实目标，别停在表面。
2. ==AI 产品需求分析要切 Agent 视角：目标、能力、知识、边界。==
3. 需求拆解路径是：一句话需求 → 5W2H 提问 → Agent 四问 → 需求结构图。
4. ==用户告诉你“该不该做”，市场告诉你“值不值”，数据告诉你“能不能”。==
5. 调研不是走过场，它给你做不做的底气、怎么做的方向、说服老板的证据。
6. 竞品分析不是抄功能，而是找空位。
7. ==第一版把 Must 做扎实，比把 Could 做一半更有价值。==
8. ==宁可多转人工，也不要让 AI 在高风险场景自作主张。目标是成本，但底线是质量。==
9. 转人工不是失败，是负责任。
10. 设计图做得越清楚，Coze 映射就越顺，搭建只是把想好的东西连起来。
