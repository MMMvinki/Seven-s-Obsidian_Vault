# 05-demo搭建：用 Vibe Coding 构建产品 Demo

> 当前笔记基于课件 PDF 整理；本课暂未提供视频转写。课件中可直接复用的提示词、Checklist、金句和工作表达已经融合到对应章节里，后续如果补充视频文字稿，可以继续增强老师口播重点。

## 一句话主线

上一课已经把“AI 客服”从需求拆到了 Coze 工作流；这一课解决的是：==如何把后台逻辑变成一个能打开、能点击、能演示、能说服老板和验证用户反馈的产品 Demo。==

完整路径是：

`需求分析 → Coze 工作流 → Vibe coding 前台界面 → 部署链接 → 接 Coze API → 可演示 Demo`

> [!tip] 本课总公式
> ==Demo 的价值不是“做完产品”，而是用最小成本把核心价值变成看得见、摸得着、能被反馈的东西。==

## 1. 从“逻辑跑通”到“能演示的产品”

课件指出当前状态和差距：

| 现在有的：Coze 工作流 | 老板真正想看的 |
|---|---|
| 一张节点连线图 | 一个能打开的链接 |
| 只有你能在 Coze 后台看到 | 一个长得像客服的界面 |
| 老板打不开、点不动 | 能输入问题、看到回复 |
| 用户完全摸不着 | 能亲手体验“这东西好不好用” |
| “逻辑”有了 | “产品感”还没有 |

> [!warning] 本课要跨过去的鸿沟
> ==从“逻辑跑通”到“能演示的产品”。==

这节课不是教你做一个真正上线的系统，而是教你把方案变成一个可以被看见、被试用、被讨论的 Demo。

## 2. 为什么 Demo 很重要

可以演示的 Demo 能帮你做成三件事：

| 价值 | 解释 |
|---|---|
| 对内说服 | 老板亲手点一点，胜过你讲十页 PPT，让决策者相信 |
| 对外验证 | 拿给真实用户试用，提前发现问题，比上线后再改便宜得多 |
| 自己想清楚 | 做的过程会逼你把模糊想法落地，很多问题做着做着才发现 |

> [!quote] 课件金句
> ==在 AI 时代，“快速做出能看的东西”本身就是一种核心竞争力。==

## 3. Demo 要做到什么程度

Demo 不是越完整越好，关键是抓住“能演示核心价值”这条线。

| Demo 要做到 | Demo 不必做到 |
|---|---|
| 能打开：一个链接 | 处理所有边角情况 |
| 能输入问题 | 真实的用户登录注册 |
| 能看到像样的回复 | 完整后台管理 |
| 能体现核心流程，含转人工 | 性能优化、高并发 |
| 看起来像个真客服 | 上线级稳定和安全 |

> [!tip] Demo 验收标准
> ==能让人“看懂这是什么、相信它能用”就够了，剩下的留给真正开发。==

## 4. Vibe coding 是什么

课件定义：

> 用 Vibe coding —— 一种“描述需求、AI 帮你写代码”的新方式。

它的核心流程是：

`设计 → 描述 → 生成 → 预览 → 迭代 → 部署`

对应动作：

`想清界面与交互 → 写成提示词 → AI 出代码 → 看效果 → 追加修改 → 拿到链接`

> [!warning] Vibe coding 省掉的是代码，不是设计
> ==设计从“画精细稿”变成了“说清楚”。形式变了，但“想清楚”这件事没有变化。==

Vibe coding 的几个特点：

- 第一版一定不完美，不要指望一步到位。
- 它本身就是“生成 → 改”的循环。
- AI 不会读心，描述越具体，做得越准确。
- 你可以不懂代码，但要懂好坏。
- AI 给的不一定对，你要能看出哪里不对，并提出修改。

## 5. 设计 Demo：把产品结构翻译成界面

界面设计不是从零开始，上一课的产品结构就是设计原料。

| 上一课材料 | 决定 Demo 什么 |
|---|---|
| 用户故事：用户问“我的薯片到哪了” | 决定 Demo 要演示哪个场景 |
| 产品结构：理解层 / 决策层 / 转人工 | 决定界面要体现哪些状态 |
| MVP 范围：物流查询 + 政策问答 + 转人工 | 决定 Demo 做哪几个功能 |

> [!tip] 设计 Demo 的本质
> ==设计 Demo，本质是把第一节“想清楚的逻辑”翻译成“看得见的界面”。==

### 从用户任务推导界面

把用户故事拆成屏幕上一步步发生的事：

| 用户步骤 | 屏幕上发生什么 |
|---|---|
| 用户打开 | 看到欢迎语 |
| 输入问题 | “我的薯片到哪了”出现在用户气泡 |
| 等待 | 显示“正在查询…”或“正在输入…” |
| 看到回复 | 显示物流状态 + 预计送达 |
| 或转人工 | 复杂问题显示转人工提示 |

> [!tip] 任务流转界面
> ==每一步“屏幕上发生的事”，都对应界面上要有的元素。走一遍任务流，界面需求就浮出来了。==

## 6. Demo 设计稿的 7 个维度

### 6.1 信息结构

先列清楚这个 Demo 有哪些区域：

| 区域 | 内容 |
|---|---|
| 顶部栏 | 客服名称 / logo / 在线状态，让人知道这是什么 |
| 消息区 | 对话历史：AI 和用户的消息气泡 |
| 输入区 | 输入框 + 发送按钮 |

> [!tip] 信息结构原则
> 先不管好不好看，先确认“有哪些区”，这是界面的骨架。

### 6.2 交互流

交互流 = 用户每做一个动作，界面给什么反应。

| 用户动作 | 界面反应 |
|---|---|
| 打开页面 | 显示欢迎语 + 几个常见问题按钮 |
| 点击/输入问题 | 问题作为用户气泡出现在右侧 |
| 等待 AI | 显示“正在输入…”加载提示 |
| 收到回复 | AI 气泡出现在左侧，消息滚到底部 |
| 遇到复杂问题 | 显示“正在为您转接人工”提示 |

> [!tip] 交互不靠 AI 猜
> ==把这张表写进提示词，AI 就知道每个动作该有什么反应。==

### 6.3 布局组件

把区域拆到组件级，再描述给 AI：

| 组件 | 描述 |
|---|---|
| 顶部栏 | 标题文字 + 在线状态点 |
| AI 消息气泡 | 左侧、浅色底、带头像 |
| 用户消息气泡 | 右侧、暖色底 |
| 转人工提示条 | 居中、特殊样式 |
| 输入框 | 占据底部大部分宽度 |
| 发送按钮 | 右侧圆形、金色 |

关键是用“方位 + 样式”描述每个模块，比如“用户气泡靠右、暖色底”。

### 6.4 状态清单

新手最容易漏的是界面的状态。

| 状态 | 说明 |
|---|---|
| 空状态 | 还没对话：显示欢迎语 + 常见问题入口 |
| 加载中 | AI 思考时：显示“正在输入…”动画 |
| 正常回复 | AI 答完：气泡正常显示 |
| 转人工 | 特殊提示条：“正在转接人工客服” |
| 出错 | 失败时：“网络开小差了，请重试” |

> [!warning] 状态是质量分水岭
> ==漏了状态，Demo 一用就露馅。把这 5 种状态都写进提示词，做出来的 Demo 才经得起点。==

### 6.5 细节

这些细节单独看很小，但加起来就是“像个真东西”和“一眼假”的区别：

- 发送后输入框自动清空，焦点保留。
- 新消息自动滚动到底部。
- AI 回复逐字打出来，或至少有加载过程。
- 按 Enter 直接发送消息。
- 长文本气泡自动换行、不溢出。
- 常见问题按钮点击后直接发送。

### 6.6 风格

风格要写清楚：配色、字体、圆角、留白、参考对象。

零食/家居电商 AI 客服可以用：

- 暖色调：米色背景 + 橙棕点缀。
- 圆角：气泡和按钮都用圆角，显得 friendly。
- 留白：消息之间有呼吸空间。
- 参考：像微信客服或淘宝客服那样亲切。

课件给了一个技巧：

> ==给 AI 一个参考对象，比如“像微信客服那样”“像 Apple 风格”，比堆形容词更准。==

### 6.7 平台

| 电脑端 Demo | 手机端 Demo |
|---|---|
| 适合会议室投屏给老板 | 适合发链接让人随手点 |
| 屏幕大，布局从容 | 更贴近真实客服场景 |
| 对话区可以居中留白 | 布局要紧凑 |
| 第一版推荐先做 | 可作为第二版优化 |

> [!tip] 平台要写进提示词
> 选定一个平台写进提示词，比如“做成桌面端网页”，AI 的布局就不会两头不讨好。

## 7. 常见设计风格与提示词表达

课件列了几类常见风格，可以作为以后写 UI 提示词的风格词库：

| 风格 | 特征 | 提示词表达 |
|---|---|---|
| 极简主义 | 大量留白、单色调、无装饰、内容优先 | 极简、大量留白、像高端杂志、只用黑白灰、无圆角、无阴影、无颜色装饰 |
| 玻璃态 | 磨砂玻璃半透明、渐变底色、白色细描边、背景模糊 | 磨砂玻璃质感、深紫渐变背景、半透明卡片、rgba 白色描边、柔和光晕叠层 |
| 新拟物 | 双向阴影、元素从背景凸起、纯色调、触感真实 | 新拟物风格、浅灰背景、双向投影、无边框、像软橡皮泥被按压的质感 |
| 赛博朋克 | 霓虹发光、纯黑底色、等宽字体、网格纹理、双色对撞 | 赛博朋克、纯黑背景、霓虹绿发光文字、热粉色描边、等宽字体、网格底纹 |
| 布鲁塔主义 | 粗黑边框、偏移实色阴影、强对比配色、未完成感 | 布鲁塔主义、亮黄背景、3px 粗黑边框、8px 偏移实色阴影、无圆角、无渐变 |
| Y2K 复古 | 糖果渐变、圆润元素、粉紫霓虹、可爱混乱 | Y2K 复古、粉紫糖果渐变、像旧版 Windows 窗口标题栏、闪亮、圆润 |
| 暗黑奢华 | 近黑底色、金色克制点缀、衬线字体、仪式感 | 暗黑奢华、深黑背景、金色细节点缀、Playfair 衬线字体、极度克制、像高端腕表官网 |

风格选择要和感觉匹配：

| 想传达的感觉 | 推荐风格 |
|---|---|
| 专业、可信、内容为王 | 极简主义 |
| 现代感、层次、科技感 | 玻璃态 |
| 柔软、温暖、亲近感 | 新拟物 / 有机 |
| 炫酷、未来、黑客 | 赛博朋克 |
| 态度、个性、反主流 | 布鲁塔主义 |
| 怀旧、可爱、社交属性 | Y2K 复古 |
| 高级感、稀缺、距离感 | 暗黑奢华 |

## 8. 文字版界面设计稿

课件把设计稿整合成一张表：

| 维度 | 内容 |
|---|---|
| 产品 | 零食电商 AI 客服 Demo，桌面端网页 |
| 区域 | 顶部栏 + 消息区 + 输入区 |
| 组件 | AI 气泡左 / 用户气泡右 / 转人工提示条 / 输入框 / 发送按钮 |
| 状态 | 空 / 加载中 / 正常回复 / 转人工 / 出错 |
| 交互 | 回车发送、自动滚底、输入框清空、点预设问题直发 |
| 风格 | 暖色调（米色 + 橙棕）、圆角、留白、友好不正式 |
| 数据 | 用上一课 Top 高频问题做 3-4 条预设对话 |
| 范围 | 只做核心对话闭环，不做登录/后台/多页面 |

> [!quote] 设计稿到提示词
> ==这张设计稿和下一模块的提示词，是同一件事的两种形态。设计稿越具体，提示词越好写，AI 越不用猜。==

## 9. 设计阶段常见 4 个误区

| 误区 | 后果 / 解法 |
|---|---|
| 跳过设计直接写 | 脑子没想清就丢给 AI，反复返工 |
| 一上来追求好看 | 先把结构和状态定对，美化是后面的事 |
| 漏掉异常状态 | 只设计正常流程，加载/出错/空状态全忘 |
| 想一次做太全 | Demo 塞太多功能，核心闭环反而没做好 |

> [!warning] 做 Demo 也要先想清楚结构
> ==记住上一课的精神：动手前先想清楚结构。做 Demo 也一样。==

设计稿 6 条自检：

- [ ] 列清了界面有哪些区 / 组件。
- [ ] 走通了核心交互流：动作 → 反应。
- [ ] 设计了所有状态：空 / 加载 / 正常 / 转人工 / 出错。
- [ ] 定了风格：配色 / 圆角 / 留白。
- [ ] 选定了设备：电脑端 or 手机端。
- [ ] 准备了示例对话数据。

## 10. Vibe coding 提示词：五个部分

课件强调：

> [!tip] 提示词质量 = Demo 质量
> ==好提示词 = 清晰的设计 + 具体的描述 + 必要的示例 + 明确的约束。==

Vibe coding 提示词心里要有五块：

| 部分 | 例子 |
|---|---|
| 角色 | 你是一名前端工程师，帮我做一个网页 |
| 目标 | 做一个零食电商的 AI 客服聊天界面 |
| 功能 | 顶部栏、消息区、输入框、转人工提示 |
| 风格 | 暖色调、圆角、友好，像微信客服 |
| 约束 | 纯前端单页、用 React、先用假数据 |

不用每条都严格分段，但心里有这五块，就不会漏掉关键信息。

### 要点 1：先说“做什么产品”，再说“要哪些功能”

不好：一上来堆功能。

> “要一个输入框、要消息列表、要发送按钮、要转人工……”

好：先给全局定位。

> “做一个零食电商的 AI 客服聊天网页，帮用户查物流、问退换货。下面是具体功能……”

AI 有了全局印象，功能才知道往哪里放。

### 要点 2：把界面拆成具体模块描述

关键是逐个点名，别让 AI 猜布局。

示例：

```text
界面分三部分：
1. 顶部：标题栏，显示“零食小助手”和在线状态点。
2. 中间：消息区，AI 消息靠左（浅色气泡），用户消息靠右（暖色气泡）。
3. 底部：输入框 + 圆形发送按钮。
4. 特殊：转人工时，中间显示一条居中的提示条。
```

### 要点 3：给具体内容和示例数据

示例对话：

```text
用户：我买的沙发到哪了？
AI：您的订单 86731 已到本地仓，预计明天送达，需要改时间吗？

用户：怎么退货？
AI：支持 7 天无理由退货，我帮您发起，请确认商品无影响二次销售~
```

给示例数据的价值：

- 演示更可信，老板看到真实业务场景。
- 风格更贴合，AI 会参照示例语气生成其他内容。

### 要点 4：把风格说清楚，别让 AI 发挥

风格要求应该包含：

- 配色：暖色调，米色背景 + 橙棕色点缀。
- 圆角：气泡和按钮都用圆角。
- 整体参考：像微信/淘宝客服那种亲切聊天风格。
- 质感词：圆角、留白、简洁。

### 要点 5：交互细节

要逐条说给 AI：

- 按回车键直接发送消息。
- 发送后输入框自动清空。
- 新消息出现时，自动滚动到底部。
- AI 回复前，先显示“正在输入…”约 1 秒。
- 顶部放 3 个常见问题按钮，点击直接发送。

> [!warning] 细节不写，AI 默认不会做
> ==这些细节不写，AI 默认都不会做。写上了，Demo 就从“能看”变成“好用”。==

### 要点 6：明确技术约束

技术约束的目标是：给 AI 划定范围，避免它用一堆你 hold 不住的东西。

示例：

- 做成单页网页，单个 HTML 或简单 React 即可。
- 先用写死的假数据，不用接后端。
- 不需要登录注册，不需要数据库。
- 代码尽量简单，方便后面修改。

原则：

`好维护 → 好部署 → 好对接`

## 12. 第一版出来之后怎么改

不要想一次完美，用“追加提示”一点点调：

| 类型 | 追加提示例子 |
|---|---|
| 改一处 | 把发送按钮改成橙色，大一点 |
| 加功能 | 给每条 AI 消息加一个“转人工”小按钮 |
| 调细节 | 消息之间间距再大一点，气泡圆角更大 |
| 修问题 | 回车发送没生效，帮我修一下 |

> [!tip] 迭代原则
> ==一次只改一两个点。改动小，AI 不容易把别的地方搞坏，你也好检查。==

## 13. 常见翻车与修复方法

| 翻车点 | 表现 |
|---|---|
| 太笼统 | “做个客服网页” → AI 全靠猜，十次十个样 |
| 一次要太多 | 一条提示塞 20 个功能 → AI 顾此失彼、漏一半 |
| 不给示例数据 | 界面空荡荡，看不出效果，也带不出风格 |
| 不说技术约束 | AI 用复杂框架，你看不懂、改不动、部署难 |

解药：

> [!quote] 课件总结
> ==先设计、再具体描述、给示例、定约束。==

出问题时不用慌：

- 贴报错给 AI：把红色报错信息原样复制。
- 让 AI 解释代码：问“这段代码做了什么？”
- 精确描述现象：“点发送没反应”比“坏了”有用得多。
- 改几轮还乱，就让它重新生成这部分。

> [!tip] 修问题的方法
> AI 既能写代码，也能修代码、解释代码。它是你的全程搭档，别怕问。

## 14. 先用 Mock，再接真实接口

课件强调：先用 Mock 数据撑起界面，再把假逻辑换成真调用。

Mock 示例：

```js
orders = {
  "86731": {
    商品: "北欧布艺沙发",
    状态: "已到本地仓",
    预计: "明天送达"
  }
}

faq = {
  "退货": "支持7天无理由..."
}
```

为什么先用假数据：

- 界面能立刻跑起来看效果。
- 不用等后端或接口就绪。
- 演示时有真实业务的样子。
- 后面接 Coze 时，把假数据换成真调用即可。

> [!quote] Mock 数据金句
> ==Mock 数据是 Demo 的脚手架：先撑起界面，真逻辑后面再接上。==

## 15. 把控范围：Demo 不是产品

课件说：

> [!warning] 范围原则
> ==Demo 的目标是“证明价值”，不是“做完产品”。范围一散，重点就丢了。==

| 做到这里就够 | 先忍住别做 |
|---|---|
| 能聊天、能看到回复 | 历史记录、多会话 |
| 覆盖 3-4 个高频问题 | 用户登录、个人中心 |
| 有转人工提示 | 后台管理、数据看板 |
| 风格像那么回事 | 花哨动画、主题切换 |

## 16. 写完提示词：6 条自检

- [ ] 先给了产品全局定位。
- [ ] 界面按模块拆开描述了。
- [ ] 给了具体示例对话数据。
- [ ] 说清了风格：配色、圆角、参考对象。
- [ ] 写了交互细节：回车、滚动、清空、加载。
- [ ] 定了技术约束：单页、假数据、简单好改。

## 17. 接上 Coze：从假数据到真实回复

当前局限：

| 现在：假数据 Demo | 接上 Coze 之后 |
|---|---|
| 回复是代码里写死的 | 回复由 Coze 工作流真实生成 |
| 问什么都答那几句 | 意图识别、知识库都起作用 |
| 查订单是假状态 | 转人工逻辑真的会触发 |
| 换个问法就露馅 | 换问法也能正确应对 |

> [!tip] Coze 是 Demo 的大脑
> 上一课搭的工作流不会浪费，它正好成为这个 Demo 的“大脑”。

连接逻辑：

`前端 Demo → 轻量后端中转（可选但推荐）→ Coze 工作流 → 回复原路返回 → 显示到对话界面`

核心原则：

> ==Coze 当后端，前端只管收发消息和显示，逻辑一行都不用重写。==

## 18. 把 Coze 工作流发布成 API

步骤：

1. 在 Coze 里把工作流发布，开启 API 调用方式。
2. 得到 API endpoint，也就是一个 `https` 地址。
3. 生成 API Token，这是调用的“钥匙”，要保密。
4. 看文档，记下入参出参：要传什么字段、返回什么格式。

> [!quote] API 发布的意义
> ==发布后，你的工作流就从“只能在 Coze 里点”，变成“任何程序都能调用”。==

## 19. Coze API 联调提示词示例

课件给出的接口信息提示词可以整理为：

```text
目标：
把现在写死的假回复，改成调用我的 Coze 工作流 API 拿真实回复。

接口：
POST 到 https://api.coze.cn/v1/workflow/run
请求头带 Authorization: Bearer <我的Token>。

传参：
把用户输入作为 parameters 里的 user_input 字段传过去。

接收：
返回结果里的 data.reply 就是要显示的回复，解析出来填进 AI 消息气泡。

要求：
- Token 不要写死在前端，放到环境变量。
- 调用时显示加载状态。
- 失败时显示“稍后再试”。
- 把 <我的Token> 和真实地址换成 Coze 给你的。
```

注意：直接把 Token 写在前端有风险，更推荐轻量后端中转或环境变量配置。

## 20. 完整数据流

完整链路：

`用户在 Demo 输入问题 → 前端/后端带密钥调用 → Coze 工作流处理 → 返回回复 → Demo 显示对应界面`

两节课拼起来就是：

`需求分析 → Coze 逻辑 → Vibe coding 界面`

> [!tip] 两节课的完整闭环
> ==左边两格（界面 + 调用）是本节做的，中间工作流是上一节做的。需求分析 → Coze 逻辑 → Vibe coding 界面，一条线走完。==

## 21. Demo 和真产品的差异

管理预期很重要，别让人以为 Demo 就能上线给几万用户用。

| 差异 | 说明 |
|---|---|
| 扛不住大流量 | Demo 没做性能优化，几个人用没问题，几万人不行 |
| 安全没做全 | 真上线要做完整鉴权、风控、数据合规 |
| 知识库要养 | 真实回答质量要靠持续补充和调优知识库 |
| 工程化缺失 | 监控、日志、容灾、回滚这些生产能力还没有 |

> [!quote] Demo 价值边界
> ==这不减损 Demo 的价值。它已经能验证想法、说服老板、拿到反馈，这就够了。==

## 22. 老板看到 Demo 后可能怎么说

课件里的老板反馈：

- “小赵，这个有点意思啊。”
- “不错，不错不错。”
- “大致知道了。”
- “不过后端我觉得还需要细化。”
- “有些定义的还是不明确。”
- “看着不错，什么时候能上线啊？”

这里你要会接住：Demo 是验证工具，不是上线承诺。要把“能演示”和“能上线”分开讲。

可复用表达见：[[05-demo演示给老板的话术]]

## 23. 总 Checklist

### Vibe coding 提示词总 Checklist

- [ ] 先说做什么产品，再说要哪些功能。
- [ ] 把界面拆成具体模块逐个描述。
- [ ] 给真实的示例内容和数据。
- [ ] 明确指定风格：配色、调性、参考对象。
- [ ] 写清交互细节：发送、加载、空态、错误。
- [ ] 设计好多种状态：空、加载、正常、转人工、错误。
- [ ] 划定技术约束：纯前端、框架、假数据、简单好改。
- [ ] 迭代用追加提示，别想一次到位。

### 部署 + 联调 Checklist

- [ ] 部署：选一键托管或 Vercel，拿到公开链接。
- [ ] 密钥：Token 用环境变量，绝不写死在前端。
- [ ] 发布：Coze 工作流发布成 API，记下地址和入出参。
- [ ] 连接：用提示词让 AI 写调用，描述清楚接口信息。
- [ ] 跨域：前端调外部接口报错时，加轻量后端中转。
- [ ] 联调：一处处把假数据换真调用，换一处测一次。
