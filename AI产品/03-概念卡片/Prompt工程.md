# Prompt 工程

> 来源章节：[[07-提示词设计：场景拆解，构建Prompt#三、Prompt 的底层认知|Prompt 的底层认知]] · [[07-提示词设计：场景拆解，构建Prompt#十、工程级 Prompt 构建|工程级 Prompt 构建]]

## 一句话定义

Prompt 工程不是把话写得“像咒语”，而是设计模型节点的身份、规则、上下文、输出格式和防护机制，让 AI 在产品流程中稳定完成任务。

## 老师强调

> Prompt 工程已死，但 Prompt 它死不了。

这句话的意思是：早期“堆咒语式 Prompt”会被 Agent、RAG、Skill、Harness、Loop 吸收，但 Prompt 仍然是每个模型节点的控制语言。

> 我们要做的是专业，而不是使用。

如果只是使用现成 AI 产品，提示词可以越来越粗糙；如果要做 AI 产品、Agent、工作流、客服系统、知识库问答，Prompt 反而要更工程化。

## 判断一个 Prompt 是否工程化

- 是否分清 System/User。
- 是否知道任务属于转换、理解、问答、生成哪一类。
- 是否拆成身份、背景、目标、输入、输出、示例、限制。
- 是否把可变部分做成变量槽，而不是写死。
- 是否有 Few-shot、CoT、任务拆解等稳定手段。
- 是否有兜底、防注入、输出格式约束。

## 常见误区

- 误区 1：以为大模型强了，Prompt 就不重要。  
  修正：产品端的 Prompt 只是被封装了，不是消失了。

- 误区 2：把所有内容都塞进 User Prompt。  
  修正：稳定规则放 System，变化内容放 User。

- 误区 3：一个 Prompt 解决所有事。  
  修正：复杂任务要拆节点，例如“翻译 → 本土化改写”，“意图识别 → 知识库检索 → 回答生成 → 自检”。

## 自测题

1. 你能不能用 30 秒解释 Prompt 为什么没有过时？
2. 你能不能说清楚 System/User 的区别？
3. 你能不能把一个新需求判断成四大类型之一？
4. 你能不能把一个客服 Prompt 拆成七个模块？
5. 你能不能说出至少三种工程化手段：变量槽、Few-shot、CoT、任务拆解、防注入、兜底。
