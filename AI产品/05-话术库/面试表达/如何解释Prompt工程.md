# 如何解释 Prompt 工程

> 来源章节：[[07-提示词设计：场景拆解，构建Prompt#三、Prompt 的底层认知|Prompt 底层认知]] · [[07-提示词设计：场景拆解，构建Prompt#十、工程级 Prompt 构建|工程级 Prompt]]

## 30 秒版

> 我理解的 Prompt 工程不是写一句好听的指令，而是把模型节点设计成稳定的产品模块。它要解决三个问题：模型是谁、依据什么做、输出成什么样。真实业务里还要考虑 System/User 分层、上下文拼装、变量槽、Few-shot、任务拆解、兜底和防注入，这样才不是一次性演示，而是能复用、能维护、能上线的能力。

## 2 分钟版

> 我会把 Prompt 工程分成三层看。第一层是层次，稳定规则放 System，变化内容放 User；第二层是类型，先判断任务是转换、理解、问答还是生成；第三层是模块，把身份、背景、目标、输入、输出、示例、限制拆清楚。再往工程化走，就不是写长一点，而是把可变内容做成变量，把复杂任务拆成多个节点，把输出格式和兜底规则固定下来，并且处理 Prompt 注入。这样 Prompt 才能成为产品流程里的稳定组件。

## 面试官可能追问：为什么现在还要学 Prompt？

> 如果只是使用现成的大模型产品，确实很多 Prompt 被产品封装掉了。但如果我们是做 AI 产品和 Agent 设计，Prompt 仍然是每个模型节点的控制语言。RAG 解决知识从哪里来，工具调用解决怎么行动，工作流解决步骤怎么走，而 Prompt 决定每一步模型扮演谁、遵守什么规则、输出什么格式、不能做什么。所以 Prompt 不是没用了，而是被工程化了。

## 可背金句

> Prompt 工程已死，但 Prompt 它死不了。

> 我们要做的是专业，而不是使用。

> 一次写对并不难，难的是规模化、稳定化、可维护。
