# DataOS实施口径与模型选型

## 来源
- raw/DataOS答疑相关 20260603.md（维度四、五、六、九、十、十一）

## 核心内容
售前答疑中的实施与模型口径：接入层目前仍需配 JDBC 关键参数（未来自动化），AI 主要帮做字段描述与清洗辅助；ETL 根据自然语言描述自动生成 SQL/Python 代码由 runner 执行；核心使用者是 FDE/现场工程师，"MD/FDE 带着产品到一线做调研"。模型策略：生产统一落地国产模型（自训 SFT 小模型），开发用 Opus/Sonnet 但要求必须在国产/开源模型上跑通才算测试通过；多模态用 Gemini 4（口语口径）。Skill 沉淀机制让系统"越用越省"：确定性逻辑逐步编码化，不再走大模型。

## 关键数据/事实
- 数据不一致处理：AI 清洗时识别异常（如"身份证 vs 身份证号"、性别 1/0 vs M/F）、主动问询并给统一建议；难点（部门拆分导致的不一致）诚实承认需 FDE 现场了解
- 治理是多 agent 的：FDE 优先用 AI，"沉进写代码根本做不完"
- 国产化口径（原文口语）："3.6/27G 的 SFT 模型"；开源模型本地部署上下文可配 256K、有的到 1M；企业客户安全要求极高，有些国内闭源模型连 API 调用都不行
- 多模态：侨银几百万张照片约 1.5 秒/张（快则 0.5 秒），普通 4090 自跑、不走公有云
- Skill 沉淀：先调研规则→沟通 agent 生成 Skill→预警调用；审核从"AI 生成+人工审核"演进为"AI 强约束+测试集"，agent 自己跑测试改代码
- 内部迭代"几乎没怎么手写代码"（自动寻路、派单、真实地图运行均 AI 做）；Skill Creator 可自生成新 Skill
- 数据驻留：接客户已有数据中台（如用友），另接入公域数据（天气/交通/人口）形成"全域数据"决策依据
- ⚠️ 原文提示："3.6/27G""Gemini 4 开源"等是会上口语原话，进正式材料前需核对口径
