<title>数字广东售前阶段对客代表性问题合集-20260528</title>

数字广东：从本次交流看，客户关注的核心不是单点 AI 工具，而是希望围绕政府数字化、数据治理、本体建模、省域大脑、城市运行和内部研发提效等场景，探索如何用 Agentrix 的 DataOS、AgentOS 和 Agent Workforce，把分散、口径不一、层级断裂的数据和业务知识，逐步整理成可理解、可调用、可追溯、可辅助决策的智能体能力底座，并先选择一到两个真实场景做试点验证。

## **问题1）“数据库连接之后，库表和字段属性是系统自动读取 DDL 或 Schema 生成，还是需要人工再录入基础属性？”**

### **业务侧回答**

这一步我们不是让客户从零手工录入所有表和字段。Agentrix 的 DataOS 会先从客户已有数据库、数据中台、数据仓库或 API 里读取 Schema、字段、表结构和基础元数据，形成第一版数据理解框架；再把命名不清楚、口径不一致、业务含义不明确的部分标出来，让工程师和业务人员确认。这样做的好处是，前期不用靠人一张表一张表硬读，而是机器先把底稿整理出来，人再判断关键语义和业务边界。

### **技术侧回答**

技术上，我们会按 DataOS 的标准链路来做：先接入客户已有的数据仓库、数据中台、数据库和 API，不要求一开始重构原有系统；接入后做元数据、血缘和字段语义处理，再把字段映射到业务本体。大规模场景里，第一步通常是扫描 Schema、字段、备注和已有文档，形成基础理解；不清楚的字段，再由前线工程师和客户业务人员确认。所以这里不是纯人工录入，也不是 AI 一次性全自动定准，而是‘系统先扫、AI 先整理、人再确认’的工程流程。

## **问题2）“前期数据扫描大概用多大的模型？是你们训练的垂类模型，还是通用模型？”**

### **业务侧回答**

前期数据扫描不完全取决于模型参数大小，关键是任务怎么拆、上下文怎么组织、规则怎么约束。我们会根据客户的数据安全要求选择模型方案：能用私有化就优先私有化，涉及政务和敏感数据时不会默认走外部公有云模型。模型只是一部分，更重要的是 DataOS 里的本体、规则、数据血缘和人工确认机制，这些决定了结果能不能进入严肃业务场景。

### **技术侧回答**

这类数据扫描不能只看模型参数大小。我们的做法是把任务约束、上下文组织、数据本体和测试校验一起设计好，模型负责理解和生成建议，本体、规则、血缘、测试集和人工确认负责把结果管住。真正进入客户生产或敏感数据环境时，也会优先考虑国产、开源或私有化模型能否跑通。也就是说，模型不是裸跑，而是在 DataOS 和 AgentOS 的工程体系里工作。

## **问题3）“在数据采集环节使用 AI，究竟解决什么问题？只是效率问题，还是还有其他价值？”**

### **业务侧回答**

AI 在数据采集环节解决的不只是效率问题，而是把过去很难规模化完成的数据理解工作变成一个可辅助、可复核的流程。比如面对大量表、字段、接口、文档和代码集差异，人工很难全部读完并建立关系；AI 可以先帮工程师发现疑点、生成清洗建议、提示口径冲突，再由人确认。对客户来说，这相当于把数据治理从‘纯人力盘点’变成‘机器先发现，人再判断’。

### **技术侧回答**

AI 在数据采集环节主要解决三个问题。第一，把结构化、非结构化数据先整理成模型能理解的本体材料；第二，在超大规模字段场景下先发现关系、异常和口径冲突，比如大量表和字段靠人完整读完并不现实；第三，辅助生成清洗或转换代码，例如根据问题描述生成 SQL 或 Python，再由执行器运行、工程师确认。它提升的不只是效率，也提升数据治理的可发现性、可复用性和可追溯性。

## **问题4）“本体里的对象、关系和动作，是提前预设好的，还是 AI 在业务领域里自己生成？还是由业务理解先定义元数据？”**

### **业务侧回答**

对象、关系、动作这三个概念，是我们用来描述业务世界的统一框架；但具体到数字广东的场景，哪些是对象、哪些是关系、哪些动作能触发，必须来自你们自己的数据、制度、流程和业务经验。我们不会拿一套固定模板套所有客户，也不会让 AI 自由发挥。更稳妥的方式是：AI 先根据数据和材料生成建议，业务专家和工程师再确认，最后沉淀成这个场景自己的本体。

### **技术侧回答**

对象、关系、动作这三个大类，是我们对业务世界的统一抽象框架；但每个场景里具体有哪些对象、关系和动作，要来自客户自己的表、字段、制度、流程和业务文档。动作尤其不能只从字段里推，它主要看业务规则、安全约束和企业流程。AI 可以生成候选本体，但最终要由业务专家和前线工程师确认，特别是动作类能力，进入执行前必须受权限、审计和人工确认约束。

## **问题5）“这个本体和知识图谱里提取三元组关系有什么区别？”**

### **业务侧回答**

可以把知识图谱理解成告诉系统‘谁和谁有什么关系’，而我们的本体要再往前走一步：它还要告诉系统这些关系在业务里意味着什么、能触发什么动作、受哪些规则限制、结果怎么追溯。也就是说，本体不是只为了看图谱，而是为了让 Agent 能基于这些关系去分析、问数、预警、生成建议和推动闭环。

### **技术侧回答**

本体和知识图谱确实有共同点，都是在描述实体和关系。区别在于，我们不是只把三元组做出来给人看，而是把数据表、业务对象、关系、动作、血缘和工具调用都组织成 Agent 可用的语义底座。本体里的关系描述要能被切片、能渐进披露，避免直接把大图谱塞给模型导致上下文爆掉。所以本体更偏向‘让 Agent 能稳定调用、解释和执行’，不只是‘把关系展示出来’。

## **问题6）“动作是作为知识图谱里的属性，还是一种额外的行为机制？动作到底怎么抽取？”**

### **业务侧回答**

动作不是普通属性，它更像业务里可以被触发、被审批、被执行、被追踪的一类行为。比如预警、派单、复核、调参、生成报告、发起工单，这些都不能只靠字段关系推出来，还要看制度、权限、流程和专家经验。我们通常会先让 AI 根据材料生成动作建议，再由客户业务人员确认哪些能做、哪些只能提示、哪些必须人工审批。

### **技术侧回答**

动作不是知识图谱里的普通属性，而是业务里的可执行行为集合。它主要来自企业规则、安全约束、流程和业务常识，比如哪些操作必须一起发生、哪些流程必须人工确认。上层 Agent 最终会通过 MCP、API、函数或 Skill 调用工具，所以动作抽取之后还要被封装为受控工具。像水务这类场景，可以拆成观察、诊断、规划、执行几个环节：先采集数据，再判断状态，再生成方案，最后在授权范围内执行。

## **问题7）“如果企业有结构化数据，也有非结构化文档，是不是会合在一起让 AI 理解，再抽取对象、关系和动作？”**

### **业务侧回答**

是的，真实项目里不能只看数据库。很多关键业务知识在制度、手册、审批流程、接口文档、会议纪要和专家经验里。Agentrix 的 DataOS 会把结构化数据和非结构化材料一起纳入语义理解范围，先把它们整理成统一的认知材料，再抽取对象、关系、规则和动作。这样 Agent 后续不是只会查表，而是能理解业务背景再给出建议。

### **技术侧回答**

是的，结构化数据和非结构化材料都要进入 DataOS。除了数据库和 API，SOP、制度、手册、合同、证照、检修手册等材料也可以做语义关联和本体建模。复杂场景不能只靠一句提示词，要先把部门文档、API、优秀样本、业务材料和调研结果组织成知识体，再辅助生成对象、关系和动作。这样 Agent 不是只会查表，而是能结合业务背景和数据血缘回答。

## **问题8）“数据量非常大时，模型上下文有约束，接近极限会变差，这个事情怎么解决？”**

### **业务侧回答**

大规模数据场景不能把所有材料一次性塞给一个模型。我们的方式是先把数据和知识按业务域、任务和关系拆开，沉淀到 DataOS 里；Agent 执行任务时，只取当前任务真正需要的本体、工具和知识片段。这样模型不是背着全量数据硬跑，而是在一个可调度、可追溯的体系里按需取数、按需分析。

### **技术侧回答**

上下文问题不能靠单个模型硬扛。我们的做法有两层：第一，把已有知识按领域和问题切片，形成强关系的知识块，像 Skill 一样渐进披露；第二，复杂任务用树形或集群式多 Agent 拆分，每个 Agent 只拿自己任务需要的有限上下文，再向上汇总。再结合 AgentOS 的记忆管理和上下文压缩机制，整体上是用 DataOS 的本体索引、知识切片、多 Agent 调度和工具调用共同解决上下文上限问题。

## **问题9）“本体或图谱在系统里是用专门图数据库存储，还是用关系型数据库？性能会不会受限制，尤其多跳查询时？”**

### **业务侧回答**

这里要分清两件事：一是本体关系和业务语义怎么组织，二是真实业务数据怎么查询。我们不会简单要求客户把所有数据搬进一个图数据库，而是会基于客户已有数据库、湖仓、中台和接口，建立一层语义和工具调用能力。具体底层用关系型、分析型、图能力还是时空数据库，要看客户现有架构、数据规模和查询场景。

### **技术侧回答**

这里要区分本体定义和真实业务数据。本体定义、对象、关系、规则和索引，可以存成关系型数据库里的结构化描述，它不是简单把所有图实例塞进图数据库。真实业务数据可以仍然在客户原有数据库、湖仓、OLAP/OLTP 系统或专用引擎里，通过语义层生成查询和跳转。遇到多跳、高并发、时空或复杂图计算场景，我们会按场景选合适的查询引擎，不会用单一存储方式包打所有场景。

## **问题10）“能不能用一个具体实例说明：用了几张表，抽取了多少对象、多少关系、多少动作，是怎么得到的？”**

### **业务侧回答**

这个问题非常适合单独做一次样例演示。我们可以拿一个脱敏场景，把原始数据表、字段含义、业务背景、抽取出的对象、关系、动作和人工确认点串起来讲清楚。贵方真正需要看到的不是概念，而是从几张表、几份文档，到一个可问、可查、可触发任务的 Agent 链路，是怎么一步一步长出来的。

### **技术侧回答**

技术链路可以这样看：先经过数据治理得到结果表，再结合场景和字段描述，让模型抽取对象、关系和动作。比如一个反欺诈或政务服务样例，可以明确接入了哪些表和文档，抽取了多少对象、多少关系、多少动作，哪些由 AI 生成，哪些由人工确认，最后如何通过 AgentOS 调用工具完成问数、预警或报告生成。这样比单独讲架构更能体现落地能力。

## **问题11）“你们说的场景是指一句话输入，还是也对应一些知识片段和业务文档？”**

### **业务侧回答**

真实项目里的场景不应该只是一句话。一句话适合演示触发，但落地时，一个场景应该包含业务目标、数据范围、制度规则、流程文档、接口说明、历史案例和评价标准。我们会把这些材料整理成场景包，让 Agent 在回答和执行时有依据，而不是只靠一句提示词猜。

### **技术侧回答**

真实场景不是一句话输入。一句话只能作为演示入口，落地时要有完整场景包。复杂场景下，要把企业文档、API、业务材料、优秀样本、调研结果先组织成知识体；Skill 的 reference、script、example 等材料也会随任务渐进式调用。也就是说，我们会把表结构、字段说明、数据血缘、业务规则、SOP、权限边界和测试样例都纳入 DataOS，AgentOS 执行时再按需调用。

## **问题12）“不同系统里的代码集不一样，比如性别有的用 1/0，有的用 man/woman/未知，这类差异怎么用 AI 处理？”**

### **业务侧回答**

这类问题我们在政企客户里一定会遇到，而且它往往是数据治理最耗人的地方。我们的做法不是要求客户先把标准准备完，而是让 AI 先扫描字段取值、命名、代码集和口径差异，生成疑点清单和映射建议；再由工程师和业务人员确认。确认后的规则会沉淀下来，后续同类系统接入就可以复用。

### **技术侧回答**

代码集差异属于数据治理里的典型问题。比如身份证、身份证号、性别代码在不同系统里表达不同，AI 可以先发现异常和同义项，再提出合并、映射或清洗建议；对于 1/0、man/woman、未知等代码集差异，可以由 AI 生成 SQL 或 Python 清洗规则，再由工程师确认。更重要的是，这些转换规则要留下版本、来源和审计记录，后续才能复用和追溯。

## **问题13）“能不能理解为这个数据治理平台是机器先做、人工确认，并把治理过程标准化的工具？”**

### **业务侧回答**

可以这样理解，而且这正是我们认为更稳的落地方式。Agentrix 不是把人排除在外，而是让机器先完成大量重复识别、规则草拟、代码生成和异常发现，让工程师和业务专家把精力放在关键判断上。对数字广东来说，这个方式可以把一个项目里的数据治理经验沉淀成流程，再逐步复制到其他业务域。

### **技术侧回答**

可以这么理解，而且要强调‘机器先做、人工确认、平台沉淀’。DataOS 的核心链路就是数据接入、治理、语义映射、本体建模、工具封装和审计血缘；AI 会反向发现字段问题、生成处理建议和代码，工程师再确认业务含义。这样治理过程不是一次性项目经验，而是可以沉淀成规则、Skill、工具和审计链路，后续同类场景可以复用。

## **问题14）“数据治理里是不是也会用多个 Agent 来完成？”**

### **业务侧回答**

复杂的数据治理任务更适合多 Agent 分工。比如一个 Agent 做元数据解析，一个做字段口径对齐，一个做清洗脚本建议，一个做规则测试，一个做审计报告。每个 Agent 做自己边界内的事情，再由人确认关键结果，这比让一个模型从头到尾处理全部问题更稳。

### **技术侧回答**

复杂数据治理会用多 Agent。单个 Agent 不适合承担大规模复杂任务，需要把任务拆给不同 Agent，每个 Agent 处理自己的工作域，再汇总。落到数据治理，可以拆成元数据解析、字段口径比对、异常发现、清洗代码生成、测试验证、血缘记录等多个任务。多 Agent 的价值不是让模型自由发挥，而是把复杂任务拆小、可控、可审计。

## **问题15）“有没有考虑通过扫描代码、API 或现有系统调用流程来生成业务动作？”**

### **业务侧回答**

这个方向我们认为非常有价值。很多企业和政府系统的真实业务动作，并不只写在制度里，也沉淀在代码、接口、日志和工作流里。如果客户允许，我们可以把这些材料作为补充输入，帮助识别系统实际怎么运转、哪些动作可以封装成工具、哪些流程必须人工审批。它适合作为试点里的增强能力逐步验证。

### **技术侧回答**

这个方向可以做。我们可以把代码、文档、手册和 AST 结构组织成知识库，用自然语言询问某个调用流程怎么走、业务逻辑是什么。对客户系统来说，如果有 API 文档、代码库、调用日志或工作流记录，就可以辅助识别业务动作和工具封装点。只是这一步受客户代码质量、安全权限和系统开放程度影响较大，建议先从只读分析和流程识别开始，再逐步封装成 MCP、API 或 Skill。

## **问题16）“从拿到项目、开始数据梳理，到形成可用的本体设计，大概要经过多少轮迭代？通过什么方式持续优化？”**

### **业务侧回答**

我们更建议按小闭环推进，而不是一开始追求全域建完。通常可以先选一个高价值、边界清晰、数据可获得的场景，用一到两个月拉出第一版数据接入、本体建模和 Agent 调用闭环；再根据业务反馈、真实执行效果和数据问题做两到三轮迭代。半年更适合理解为从进入客户到试点跑出可见成果的周期，不是说前期要等半年才有第一版能力。

### **技术侧回答**

本体建设要小闭环迭代。比较现实的路径是早期 POC 和 MVP 先在一到两个月拉出闭环，再通过试点扩大。前期核心不是先做一个漂亮界面，而是让 Agent 和数据治理方法先跑通。对数字广东，我们建议先选一个场景做初版本体，再通过业务反馈、执行结果、错误样本和审计记录做两到三轮迭代，稳定后再复制到其他业务域。

## **问题17）“多模态场景用什么模型处理？是公有云能力还是本地能力？”**

### **业务侧回答**

多模态场景要根据安全要求和实时性来选。比如低空智控、城市治理、环卫巡检、政务热线和语音智能体，都涉及图片、视频、语音、位置和业务数据的融合。我们可以根据客户要求选择本地化、私有化或客户认可的模型方案；对政府客户，优先考虑数据安全、部署边界和可审计性，而不是简单追求某个模型品牌。

### **技术侧回答**

多模态能力要结合场景选模型和部署方式。图片、视频、轨迹、GIS、船舶、航班、卫星和工单数据，都可以汇聚到统一时空底座；DataOS 也可以同时接入结构化和非结构化数据。对图片识别、巡检、语音交互这类场景，可以使用私有化、本地化或客户认可的模型；对政府客户，优先要看数据安全、延迟、算力和国产化要求。模型输出还要进入本体和任务流程，不是孤立识别。

## **问题18）“不同场景下什么时候需要预警、什么时候不预警，是定制方案，还是用通用模型能力？靠提示词解决吗？”**

### **业务侧回答**

预警规则一定要结合业务定制，不能只靠通用模型或一句提示词自由判断。通用模型可以帮助理解材料、生成规则草案和解释原因，但什么时候预警、预警等级怎么分、是否派单、是否升级，都要根据客户的管理规则、风险容忍度和处置流程来确定。我们更建议先把规则沉淀成 Skill 或工具，在试点中持续校准。

### **技术侧回答**

预警不能只靠通用模型或提示词。通常先通过调研描述规则和约束，再让 Agent 生成 Skill；规则稳定后，把确定性的东西逐步代码化，减少每次都让大模型判断。水务类场景可以很好说明这个逻辑：观察者采集传感器和监控数据，诊断者判断状态，规划者生成方案，执行者在规则范围内行动。对政府场景，我们建议先做预警和辅助研判，派单、处置、调度、定责都要有人工确认和审计。

## **问题19）“规则沉淀和 Skill 生成过程是 AI 总结后人工确认，还是工程师来做？”**

### **业务侧回答**

早期更适合 AI 生成、人工审核。AI 可以根据业务材料、历史案例和流程规则生成 Skill 草案，工程师和业务专家再检查它是否符合实际工作。等这个规则经过多次验证后，我们可以把确定性部分代码化、工具化，减少后续重复配置成本。

### **技术侧回答**

规则和 Skill 的沉淀路径是：早期 AI 生成，人工审核；规则稳定后，做测试集，让它必须通过测试才算可用；高频、确定性的部分再沉淀成代码、函数或 MCP 工具。Skill 不是简单提示词，它还可以包含脚本、参考材料和示例，相当于一个可复用的岗位能力包。这样 AgentOS 调用 Skill 时，既有自然语言理解，也有确定性工具链。

## **问题20）“对于全域数字化转型，你们当前有什么业务切入点？最大价值是什么？”**

### **业务侧回答**

全域数字化转型不能从一张大蓝图直接覆盖所有部门。我们建议从一个真实业务域切入，比如应急、水利、自然资源、政务服务、城市运行或百千万工程，先把数据接入、本体建模、Agent 辅助研判和执行闭环跑通。它最大的价值不是再做一个大屏，而是让领导和业务人员能更快看到问题、理解原因、获得建议，并且知道这个建议来自哪些数据和规则。

### **技术侧回答**

全域数字化更适合从 DataOS 到 AgentOS 再到岗位智能体逐步推进。底层是数据接入，中间是语义本体，上层是工具和 Agent；时空平台和世界行为模型方向，则说明多源时空数据可以支撑城市运行分析和推演。对政府侧，我们不建议先做一个大而全的大屏，而是先选择应急、水利、自然资源、政务服务或城市运行中的一个闭环，把数据、规则、工具和 Agent 跑通，再逐域扩展。

## **问题21）“政府侧数据和企业不一样，省、市、区县、街道之间很多是人工报数，数据断层、口径不统一，这类问题怎么解决？”**

### **业务侧回答**

这个问题非常现实。政府侧项目的难点往往不是模型，而是数据产生机制、上报机制和跨层级协同机制。我们不会说 AI 可以凭空解决所有数据断层，而是会先帮客户把断点、口径差异、缺失字段和上报链路梳理出来，再选择一个有真实业务闭环的场景先做治理。数据没有的地方，要通过机制补齐；AI 的价值是让问题更快暴露、更容易被管理。

### **技术侧回答**

政府侧的数据断层，不能靠模型凭空补齐。AI 能帮忙发现数据缺口、字段冲突、口径差异和血缘不清，但真实数据仍然来自业务系统、人工上报或基层采集机制。DataOS 可以先做只读接入、元数据扫描、口径映射和数据质量清单；AgentOS 可以把缺口转成任务、复核和报告。没有数据的地方，需要客户通过管理机制补采，AI 的价值是把问题暴露得更快、更清楚。

## **问题22）“你们有没有做 119、120、110 调度这类行业？整个体系下来有几个产品，除了 DataOS 还有什么？”**

### **业务侧回答**

应急、公安、医疗急救这类场景和我们的城市治理能力方向是匹配的，但这类场景责任重、实时性高，不能一上来承诺自动调度。我们的产品体系可以简单理解为三层：DataOS 做数据和知识底座，AgentOS 做智能体调度、权限、审计和系统对接，Agent Workforce 做面向岗位的数字员工。具体到 119、120、110，更适合先从辅助研判、预警提示、工单流转和人工复核切入。

### **技术侧回答**

产品体系可以用四层架构来解释：底层是数据接入，中间是语义本体，上面是工具/API/MCP，再往上是业务人员使用的 Agent。换成产品就是 DataOS、AgentOS 和 Agent Workforce。CityLoom、CityPilot、低空智控、环卫治理、时空平台，都属于这个体系的不同应用形态。119、120、110 这类场景涉及实时调度和公共安全，更适合从辅助研判、预警提示、工单流转和人工复核试点，不宜直接承诺自动调度。

## **问题23）“你们展示的时空平台是一个模型，还是一个数据存储和查询系统？是在训练世界模型，还是为世界模型收集训练数据？”**

### **业务侧回答**

可以先把它理解成一个时空数据融合和智能分析底座，而不是直接等同于成熟世界模型。它把飞机、船舶、卫星、摄像头、GIS、时间轴和业务数据汇聚到统一空间里，让用户能查询、关联、分析和辅助判断。未来可以往更强的推演和预测发展，但对客户沟通时，我们会先把它定义为多源时空数据融合、问数和辅助决策平台。

### **技术侧回答**

这个时空平台当前更稳妥地理解为多源时空数据融合和分析底座，不是直接等同于已经成熟的世界模型。它可以接入飞机、船舶、卫星、摄像头、GIS、时间轴、工单和公开数据，先做查询、关联、分析和辅助判断。未来可以向世界行为模型和推演方向发展，但真正训练可泛化的世界模型，还需要长期数据、任务定义、规则体系和验证机制。对客户沟通时要把当前能力和研发方向分开说。

## **问题24）“如果用户问‘某个事件会不会发生’，例如战争是否发生，本体里要怎么对这些行为做建模？”**

### **业务侧回答**

这类问题不能让模型凭感觉回答，而是要把事件、主体、行为、证据、时间和空间关系组织起来。比如应急场景，不只是看天气，还要看人口、道路、物资、历史积水点、排水能力和处置资源。我们能做的是把证据链和影响因素组织起来，给出辅助判断和推演建议，让人更快做决策，而不是替人做绝对预测。

### **技术侧回答**

这类事件判断要建模成对象、关系、状态、行为、时间和证据链。单个数据意义有限，但船舶、航班、卫星、气象、工单、人口和基础设施数据叠加后，就能支撑更复杂的判断。基本对象和关系相对稳定，具体行为会跟业务关联。技术上，我们让 DataOS 组织证据和本体，让 AgentOS 调用工具形成分析和推演建议。高影响事件只能做辅助研判，不能说成绝对预测。

## **问题25）“我们内部有没有工具需求？在 AI 原则下，产品研发、测试、运维现在怎么协作？”**

### **业务侧回答**

这其实是双方很适合先做的低风险切入点。数字广东有大量业务专家和传统研发工程师，如果能把研发规范、测试流程、运维知识、客户方案和项目经验沉淀成 Skill 和 Agent 工作流，就能先在内部提升效率，再把成熟方法带到政府客户项目里。这个方向不用一开始碰核心业务系统，也更容易快速验证价值。

### **技术侧回答**

内部工具可以从 Skill 和 Agent 工作流开始做。Skill 是角色任务描述加脚本、参考材料、示例，可以像岗位能力包一样复用；内部开发、测试、运维也可以用 AI 生成代码、跑测试、根据目标驱动迭代，但要通过测试集和人工审核。对数字广东内部研发、测试、运维，可以先把规范、SOP、测试用例、运维知识、客户方案沉淀成 Skill，再通过 AgentOS 对接代码仓库、工单、办公系统或 CLI，但实际操作必须有权限和审计。

## **问题26）“能不能先挑一两个正在落地的场景做探索验证，行了再复制到其他领域？”**

### **业务侧回答**

这个推进方式我们非常认可。双方不需要一开始就做全域大平台，可以先选一到两个数字广东已经在推进、数据相对可获得、业务负责人明确的场景，组建小团队做 POC。只要第一个场景能跑通 DataOS 的数据接入和本体建模，再跑通 AgentOS 的问数、预警、报告或任务闭环，就能沉淀方法，再复制到水利、自然资源、应急、政务服务或百千万工程等领域。

### **技术侧回答**

这个推进方式和我们的技术路径是一致的。DataOS 底座要先建扎实，复杂场景必须通过调研、知识体、本体和迭代逐步跑通；水务、时空和多模态案例也都是从具体业务问题切入。建议数字广东先选一到两个已有真实需求、数据相对可得、组织配合明确的场景，先做只读接入、本体初版、工具调用和人工复核闭环。跑通后，再把沉淀的本体、Skill 和 Agent 方法复制到更多领域。

# **一）三层知识卡片**

### **第一层：绝对可说**

- Agentrix 的整体架构包括 DataOS、AgentOS 和 Agent Workforce 三层。
- DataOS 可以把分散数据和知识整理成智能体可理解、可调用的认知材料。
- AgentOS 可以承载多智能体协作、系统对接、权限控制、行为审计和回滚治理。
- CityLoom 可以支撑城市知识图谱、多源数据融合和城市运行分析。
- CityPilot 可以支撑城市治理中的派单、执行、反馈和复盘闭环。
- VoiceAgent 可以支撑自然语言语音交互、语音识别、语音合成和低延迟服务体验。
- 对政府客户更适合先做试点验证，再逐步扩展到更多业务域。

### **第二层：可以说，但要加前提**

- 可以支撑政务、应急、水利、自然资源等方向探索，但依赖客户数据、接口、权限和业务规则条件。
- 可以提升数据治理和本体建模效率，但关键语义、口径和动作规则需要人工确认。
- 可以做预警、辅助研判、问数和报告生成，但调度、审批、处置和定责要保留人工确认。
- 可以适配不同模型和部署方式，但要结合客户安全要求、算力条件和国产化要求评估。
- 可以从内部研发、测试、运维工具切入，但涉及实际系统操作时要有权限控制和审计。

### **第三层：不要说满**

- 不要说“所有数据都能自动理解并一次性完成治理”。
- 不要说“只靠大模型就能解决政府侧数据断层和口径不统一”。
- 不要说“可以直接替代政府人员做调度、审批或处置”。
- 不要说“所有系统都能无缝接入，不需要客户配合”。
- 不要说“Agentrix 已经成熟支持所有全域数字政府生产场景”。
- 不要说“世界模型已经可以稳定自动预测重大事件并替代人工决策”。

# **二）以后回答客户时，优先用这个句式**

### **推荐统一句式**

- “我们当前已经能做的是，把客户现有数据、文档、系统和业务规则先接入到 DataOS，形成可理解、可调用、可追溯的语义底座。”
- “在这个底座之上，AgentOS 可以把问数、分析、预警、报告、派单和复核等能力封装成 Agent、Skill 或工具调用。”
- “这个方向技术上匹配，但落地范围要看你们的数据基础、系统接口、权限边界和业务规则成熟度。”
- “更建议先选一到两个真实场景做试点，把数据接入、本体建模、工具调用和人工复核闭环跑通，再逐步复制到其他领域。”
- “AI 在这里不是替代业务人员，而是先做大量识别、整理、建议和生成工作，关键判断仍由业务专家和管理人员确认。”
- “涉及调度、审批、处置和定责的场景，我们建议先定位为预警和辅助研判，等规则、权限和审计机制稳定后再讨论更深的自动化。”

这个句式会让整体对客口径更稳定，也更贴合 Agentrix 的真实能力边界。
