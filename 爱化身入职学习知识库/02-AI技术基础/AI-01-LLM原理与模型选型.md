# AI-01｜LLM 原理与模型选型

> [!info] 事实边界

## 1. P0：先建立一个可用于售前的解释

大语言模型把输入转换成 token 序列，根据已看到的上下文，逐步预测后续 token。它经过海量训练，形成了语言表达、模式识别、知识关联与一定的推理能力。它可以理解“昨晚这条路为什么没扫”，但仅靠模型参数并不知道昨晚某一辆清扫车的真实轨迹。

把企业应用拆成四件事，就不会把所有能力都归给“大模型”：

| 客户任务 | 主要责任组件 | 必须核实的条件 |
|---|---|---|
| 理解“没扫”指漏扫、未达标还是没记录 | LLM、业务术语和上下文 | 用户意图与“完成”定义 |
| 找到道路、合同、班组、轨迹和投诉 | 数据底座、检索、SQL/API | 数据覆盖、关联键、更新时间、访问权限 |
| 判断是否触发补扫、派谁去 | 业务规则、优化算法、LLM 辅助 | 班次、车型、人员资格、道路约束 |
| 实际派单并确认完成 | 业务 API、工作流、审批和回执 | 服务器鉴权、幂等、执行结果 |

因此，模型是语言与决策辅助能力，企业系统还要提供事实、规则、执行与治理。对 Agentrix，可据公司介绍解释为：Data OS 提供业务数据与统一语义，Agent OS 编排能力与工具，Agent Workforce 面向岗位交付任务；**每项具体能力仍要在当前产品环境验证**。

大模型的基本语言建模目标可写为：

$$P(x_1,\ldots,x_T)=\prod_{t=1}^{T}P(x_t\mid x_1,\ldots,x_{t-1})$$

“高概率”表示训练与上下文条件下比较合理的续写，不等于事实已经在业务数据库得到验证。这是为什么一段很流畅的解释仍可能编造工单号。公司数据接入、本体映射和工具执行的重要性，正来自这一差异。

## 2. P1：token、Embedding、Attention 到底是什么

**Token 是模型处理的离散单位。**它可能是一段词、一个字、标点或编码片段，取决于分词器；“一个中文字符等于一个 token”不是通用规则。输入成本、上下文上限、输出预算通常与 token 有关，售前估算要用目标模型的分词器或 usage 实测。PDF 有 100 页，也不能直接换算为 token：扫描图、表格结构与重复页眉都会改变处理量。

**Embedding 是把对象表达为向量。**模型内部有 token 表示；检索应用还常用专门的 Embedding 模型，把问题和文档片段编码成适合比较的向量。两者相关，但不要把“大模型内部向量”和“知识库检索向量”当成同一个接口。向量相近说明编码模型认为它们相关，不说明两个对象业务上相同。“清扫车”和“洒水车”可能语义相近，但任务资格不能混用；车辆 ID 应由主数据确定，不能让相似度决定身份。

**Attention 让一个位置在生成表示时使用其他位置的信息。**经典缩放点积注意力：

$$Attention(Q,K,V)=softmax\left(\frac{QK^T}{\sqrt{d_k}}\right)V$$

可把 Q 理解为当前寻找的信息，K 是可匹配的特征，V 是被聚合的内容。模型读“张师傅驾驶 A 车，李师傅驾驶 B 车；他临时请假”时，需要利用关系和上下文，但代词本身仍可能歧义；不是用了 Attention 就永远不需要澄清。原始 Transformer 使用多头注意力及前馈网络，最初针对序列转换任务，并非今天每种模型架构细节的完整说明。[Transformer 原论文](https://arxiv.org/abs/1706.03762)

生成模型通常逐 token 解码。低温度使分布更集中，提高温度会增加采样多样性；不同模型/API 可能不开放同一组参数。**温度为 0 也不是“事实保证”，跨硬件、服务版本和执行环境也不应承诺逐字确定**。稳定交付依赖固定版本、校验、业务规则和回归评测，不能依赖一个采样参数。

## 3. P0：预训练、微调、RAG，各解决什么

预训练学习广泛的语言和世界模式；监督微调（SFT）使用输入—理想输出样本改善特定任务行为；偏好对齐（例如 RLHF）让输出更符合偏好与指令。它们都不能自动把“用户喜欢的答案”变成“现场真实发生的事情”。InstructGPT 论文展示了人类示范与偏好反馈的训练流程，同时也明确保留错误的存在。[人类反馈训练原论文](https://arxiv.org/abs/2203.02155)

RAG 在推理时取回外部知识放入上下文，通常不改变基础模型参数。工具调用则让应用向数据库或业务系统发起请求。微调可能改变模型参数或附加可训练参数。LoRA 的基本思想是冻结预训练权重，以低秩参数表示增量，降低适配时的训练负担；它不是自动获得企业实时数据的方法。[LoRA 原论文](https://arxiv.org/abs/2106.09685)

| 需求 | 优先验证 | 原因与边界 |
|---|---|---|
| 按固定字段提取投诉 | Prompt + 结构化输出 | 先证明任务可稳定定义，字段仍需校验 |
| 回答最新合同作业标准 | RAG + 版本过滤 | 知识变动快，需引用原文与生效日期 |
| 查询今天未完成工单数 | 受控 SQL/API | 实时、聚合、权限比文本相似度更重要 |
| 长期保持专业分类或固定风格 | 先建评测，再比较 Prompt 与微调 | 有足够高质量样本且收益可验证才考虑训练 |
| 多车路线与时间窗优化 | 专门优化求解器 + LLM 交互 | LLM 可解释约束、调用求解器，不应冒充已证明最优 |
| 看现场照片判断垃圾堆积 | 视觉模型 + 标注与现场复核 | 光照、遮挡、角度会影响效果，识别不等于行政认定 |

常见误区是“把所有公司文档微调进去就不需要知识库”。这会把可更新、可删除、可审计、按用户授权的信息管理问题，混到参数记忆中。实际方案可以结合微调、RAG 和工具；选择依据是误差来源与维护成本，不是哪个词更先进。

## 4. P0：模型选型是一项实验，不是排行榜竞猜

第一步先确定硬约束：数据可以进入哪些环境、现有部署资源、客户业务时延、并发量、可接受的错误类型。第二步确定任务集：环卫助手至少分开测试制度问答、对象消歧、参数提取、工具选择、异常处理和多模态识别。第三步统一上下文与工具，比较候选模型，记录失败类型。第四步在满足关键约束后比较成本与速度。

不能只用“回答写得好”决定模型。一个文案能力很强的模型，如果经常把 `road_id` 编错或不尊重证据时效，就不适合直接承担派单参数生成。相反，简单分类未必需要最强的推理模型。

选型表建议这样填写，不先填厂商排名：

| 项目 | 测量方法 | 示例记录方式 |
|---|---|---|
| 任务成功率 | 相同案例、独立留出集、多次运行 | 40 个案例，32 个全部达标；另外列关键失败 |
| 证据可靠性 | 每个关键断言核对来源 | 引用存在、内容支持、版本适用分别计分 |
| 工具可靠性 | 名称、参数、权限、结果处理分别测 | 准确选工具但参数错，不能算成功 |
| 体验与容量 | 同一环境测首响应、总时延、并发 | P50/P95；排队时间单独记录 |
| 总成本 | 全链路 token、检索、重试、人工 | 按每个合格完成任务计算 |

以上数字只示范记录格式，不是验收标准。POC 样本很少时，要同时给出原始分子分母和典型失败，不把单个百分比包装成上线承诺。具体方法见 [[AI-06-评测可观测性与成本性能]]。

## 5. P1：云端、私有化、开源、量化的工程含义

“可本地部署”至少要分别检查：模型权重和许可证、推理框架、硬件与驱动、依赖下载、外部 API、Embedding/Reranker、日志、鉴权和升级。只把 LLM 放到本地，知识库 OCR、遥测或工具仍访问外网，就不能笼统宣称端到端离线。

估算模型权重显存可从简单算术开始：`参数量 × 每参数字节数`。假设 7B 参数，以 16 bit 存储，权重约 14 GB（十进制）；这**仅是权重体积粗估**，不是“一张 14 GB 卡就能部署”。实际还需要 KV cache、激活、运行时、量化元数据和并发空间，分布式切分也会改变单卡占用。量化降低权重表示精度与体积，但质量变化要在自己的工具调用和中文业务任务上验证。

KV cache 保存生成过程中已计算的注意力键和值，减少重复计算；随着上下文、并发与架构不同，其容量压力会变化。输入很长时，即使模型能“放下”，首 token 时延也可能很差。售前不用当场报未经压测的 GPU 数量，应把请求长度、并发、模型版本和时延目标交给工程团队形成可验证配置。

## 6. P1：如何解释幻觉，并正确定位问题

“环卫车 18 点已完成补扫”可能有四种不同错误：模型无证据编造；检索返回了昨天记录；工具回执只表示接单而非完成；底层 GPS 数据本身错了。只有第一类直接属于生成失真，后面还涉及检索、语义和数据质量。

定位顺序是：先看原始输入和目标定义，再看实际送入模型的证据与工具结果，最后看生成输出是否超出证据。若输入只有“已接单”，模型说“已完成”，要修输出约束和状态映射；若工具将已接单映射为已完成，则要修接口语义。不断换更强的模型不会自动解决后者。

长上下文也有边界：经典研究发现，证据位置会影响长文本任务表现；这提示我们应测实际任务的证据利用能力，而不是只看最大窗口数字。论文结果是特定时期模型的实验，不可直接当作所有新模型的固定退化幅度。[Lost in the Middle](https://arxiv.org/abs/2307.03172)

## 7. P0：30 秒客户解释、练习与自测

**30 秒解释：**“大模型负责理解和组织信息；回答您公司的实际业务，需要连接您认可的数据和规则。比如判断道路是否漏扫，我们会查询轨迹、作业状态和合同标准，再提供可回溯结论；如果需要派单，还要经过权限、审批与执行回执。我们会用您的代表性任务验证模型和整套链路的效果。”

**15 分钟练习：**列出 5 个环卫需求，为每个选主组件：制度解释、实时车辆位置、雨天作业调整、最短调度路线、投诉摘要。写出每个任务的一条不可凭空补全信息，再补一条失败时的处理路径。答案参考：制度→RAG/现行版本；位置→API/时间戳；调整→规则+天气与调度状态/现场约束；路线→求解器/真实路网约束；摘要→LLM/原始投诉。缺失信息分别应补取证据、报告数据过期、转人工确认、提示无法计算、标记原文缺失。

**自测 1：**“把温度设为 0，就可以承诺没有幻觉吗？” **答案：**不能。采样集中度、事实正确性和服务可复现性是不同问题。

**自测 2：**“客户提供了所有合同，模型就知道今天该派哪辆车吗？” **答案：**不知道。还缺车辆可用状态、人员资格、当前任务、地理位置与业务授权。

**自测 3：**“售前必须会训练基础模型才能胜任吗？” **答案：**JD 要求理解应用技术、快速原型和边界管理；应能解释机制、判断路线、设计验证并与研发协作，深度训练研究不是从这份 JD 推导出的入职先决条件。
