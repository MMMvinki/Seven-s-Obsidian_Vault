# AI-06｜评测、可观测性与成本性能

[[00-爱化身入职学习地图]] · 前置：[[AI-03-RAG从检索到可信回答]]、[[AI-05-Agent工作流MCP与Skills]]

> [!abstract] 五天内怎么读
> **P0：第 1—4、7、9 节，约 20 分钟。**先会定义“成功”、准备代表性案例、看全链路失败和估算每个完成任务的成本。第 5—6、8 节为 **P1**。

> [!info] 数字边界
> 本篇数量、价格和耗时均为明确的教学假设，不是 Agentrix 性能、报价或验收承诺。公司材料中的提效、准确率、秒级等叙述不能直接搬到新项目；要重新对齐场景、基线、口径与证据。

## 1. P0：售前不是证明 AI 很聪明，而是证明任务可交付

Demo 成功通常意味着一个演示路径跑通；POC 应验证在约定数据、系统和场景中能否达到验收标准；生产运行还需要容量、稳定性、恢复、安全和运营责任。不要把一次顺利演示的体验，扩展成大规模稳定效果。

对于“投诉后自动补扫”，最终成功不只是模型回复“已安排”。要看是否生成了正确项目、正确道路、正确任务的工单，是否有必要授权，是否没有重复派单，以及业务要求的回执是否到达。生成文本与环境最终状态要分开评估。Anthropic 的 Agent 评测文章明确区分测试任务、重复尝试、评分器、运行记录和最终环境结果。[Agent 评测官方说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

建议把成功条件写成可以核查的语句：“对于数据完整且属于已授权项目的投诉，系统能识别唯一道路，引用现行规则，生成合法草案；需要人工授权时不能绕过；提交重试不得增加工单；证据不足时明确缺失信息。”其中授权和重复写入可作为硬性失败项，不与文案流畅度平均掉。

## 2. P0：把总分拆成四层，才能定位改哪里

| 层级 | 主要问题 | 例子 |
|---|---|---|
| 数据与检索 | 该有的数据有没有，是否正确可见 | 最新合同是否召回、是否混入其他项目 |
| 模型与工具选择 | 模型是否正确解释与提出调用 | 道路消歧、字段提取、工具参数 |
| 执行与状态 | 业务动作是否真实、合法、可恢复 | 幂等、并发、超时对账、状态转换 |
| 业务结果 | 是否帮助客户完成目标 | 处理时间、返工率、人工接管率、作业达标 |

不要只设一个“回答准确率”。对于环卫场景，“回答引用错条款”“派错道路”“统计少一单”“回复比较啰嗦”后果不同。可以用维度分数观察改进，但关键错误必须单列计数和样例。

问答常测事实正确性、证据支持、引用适用性和拒答边界。工具任务常测工具名、参数、顺序、授权、业务后置条件和失败恢复。算法建议还要测约束满足：车辆不冲突、车型正确、班次可用，而不是只看建议看起来合理。

## 3. P0：建立一个可复用的“小而有代表性”评测集

准备学习版评测时，可以从 30 个案例起步：8 个常规问答、5 个实时查询、5 个跨对象关系、4 个资料缺失/冲突、4 个权限边界、4 个提交异常。这个数量只是个人学习和首次排查的起点，不代表生产风险已经覆盖。

每个案例应保存：任务输入、用户角色与项目、数据快照或固定 mock、预期事实、允许/禁止动作、可接受最终状态、来源依据和评分方法。同一任务可以有不同正确措辞，不要把字面完全相等当作所有生成任务的正确标准。

```json
{
  "case_id": "dispatch-timeout-01",
  "category": "执行恢复",
  "user_context": {"project": "P-01", "role": "dispatcher"},
  "input": "提交已确认的 R-017 补扫草案",
  "fixture": "第一次提交已创建工单，但响应超时",
  "expected": {
    "work_order_count": 1,
    "must_preserve_request_identity": true,
    "must_query_status_before_new_submit": true,
    "allowed_final_states": ["created", "pending_verification"]
  },
  "forbidden": ["生成新的重复工单", "未核实就宣称作业完成"]
}
```

从真实项目收集案例时应去标识化，并按客户授权处理资料。评测集需要覆盖“资料有答案但问法变了”，否则只是测关键词照抄。调试样本与最终验收样本应分开；如果多份材料来自同一合同模板，最好按项目或文档来源分组切分，减少近重复泄漏。

## 4. P0：评分器怎么选，结果怎样诚实汇报

**代码规则**适合明确事实：JSON 是否可解析、引用 ID 是否存在、数据库是否恰好一单、状态是否允许、任务是否跨项目。**人工业务评审**适合语义口径、建议价值、证据充分性。**LLM-as-judge**适合大规模初筛和需要语义理解的检查，但它本身也会错，应使用清晰评分规则、人工标注校准、抽样复核和独立检查。

模型评分不能证明模型自身没幻觉，尤其当评审模型和被评模型看到同样错误证据时。调换答案顺序、去除不必要品牌信息、让评审只依据指定证据，都可以作为降低偏差的实验；最终要检查与业务专家的一致性。

可靠报告至少给出分子/分母、测试集范围、重复次数、模型和配置版本、重要失败。例如：“30 个案例各跑 3 次，共 90 次，76 次满足全部条件；按主要原因互斥归类，4 次状态误报，6 次证据不足但未明确说明，4 次接口异常未恢复；其中权限越界测试 12/12 被阻止。”权限测试属于 90 次内的子集，不另加到总样本数。同一运行可能有多个问题，若采用多标签统计则要注明各类失败数不可直接相加。这仍不是生产无风险保证，也不能把总通过率掩盖具体问题。

`pass@k` 常用于衡量尝试 k 次至少一次成功的能力；而需要日常稳定执行时，还要关心重复运行是否每次都成功。教学假设单次独立成功概率为 p，则至少一次成功为 `1-(1-p)^k`，k 次全成功为 `p^k`。若 p=0.8、k=3，分别是 99.2% 和 51.2%。现实尝试可能相关，这只是说明“多试几次总能过”与“稳定可交付”不是同一指标。

## 5. P1：可观测性让“感觉不行”变成可定位的问题

Logs 记录事件细节，Metrics 汇总计数和时延等指标，Traces 串起一次请求中的跨组件调用。Trace 中的 Span 可表示检索、模型调用或业务接口等步骤，并记录开始结束时间、状态与关联。OpenTelemetry 提供跨服务追踪的基础概念与标准化方法。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/)

教学任务的轨迹可以是：

```text
task T-017
  auth.check                 20 ms
  road.resolve               80 ms
  rag.retrieve              120 ms
  rag.rerank                 90 ms
  llm.make_proposal         1800 ms
  rule.validate              30 ms
  approval.wait            人工等待，单独计量
  dispatch.commit          1000 ms -> upstream timeout
  dispatch.query_status     100 ms -> created
  llm.explain_result        600 ms
```

应记录模型版本、Prompt 版本、索引版本、工具名、参数摘要、证据 ID、token 用量、错误类型和业务状态。这样发现“9 月 12 日效果下降”，才能区分是模型换版本、合同更新、接口字段变化还是索引同步失败。

不应默认保存全部原始敏感内容。日志要做字段脱敏、访问控制、留存期限与必要采样；调试需要原文时走受控访问。可观测性也不等于暴露完整模型内在推理，审计重点是可验证输入、实际动作、规则和结果。

## 6. P1：性能要看整个任务，不只看模型出字快不快

一次回答总耗时可拆成：鉴权与排队 + 检索/重排 + 模型输入处理 + 输出生成 + 工具调用 + 重试 + 网络。复杂 Agent 还会重复多轮。首 token 时延（TTFT）影响开始回应的体感，总任务完成时延决定业务效率，二者应该分开测。

平均时延会隐藏慢请求；P50 表示中位水平，P95 表示 95% 的样本不超过该值，但一定要记录样本量与测试负载。单用户 Demo 的 P95 不能代表高并发时的表现，压测也需要包括真实输入长度、工具延迟与模型限流。

常见优化顺序：先删掉不必要的模型调用；在数据库完成精确统计；减少无关上下文；按需加载工具和 Skill；并行独立只读请求；限制无效重试；为低风险简单任务比较更轻量模型。每次优化后回归关键评测，避免把成本降下来却让证据和权限出问题。

需要缓存时区分静态资料和动态业务数据。合同解释可按版本缓存；车辆当前可用状态需要明确短时效和重新校验；带权限的答案缓存还要包含授权范围与撤权策略。流式输出能改善等待感，但模型刚开始说话不代表任务已经完成。

## 7. P0：成本应按“合格完成任务”计算

只比较模型的每百万 token 单价，会忽略多轮调用、重试、检索、Embedding、Reranker、OCR、存储、部署和人工接管。基础式子是：

$$C_{task}=\sum_i\left(\frac{T_{in,i}P_{in,i}+T_{out,i}P_{out,i}}{10^6}+C_{tool,i}\right)+C_{infra}+C_{human}$$

这里 token 单价按每百万计，输入还可能按缓存命中等拆分，具体以供应商计费口径为准。基础设施和人工可按一致方法分摊，避免重复计费。

**纯教学算例：**假设输入 4 元/百万 token、输出 12 元/百万 token，每次 3000 输入+500 输出，则每次模型调用 `3000×4/10^6 + 500×12/10^6 = 0.018 元`。平均一项任务 3 次调用则 0.054 元；1000 项任务的模型费用 54 元。若其中 900 项合格完成，单个合格完成任务的模型费用是 `54/900=0.06 元`，还没算其他费用。这里价格是虚构算术参数，不可用于客户报价。

ROI 也应从业务基线出发：现有平均处理时间、每月任务量、人工参与比例、返工与失败损失。假设自动化节省 5 分钟，但新增 7 分钟复核，不能只展示生成速度变快。可用“净节省时间 = 原流程人工时间 − 新流程人工时间 − 新增返工时间”比较；人员时间变少不必然等于可兑现现金节省，要结合岗位安排和业务增长解释。

公司介绍里的“人车综合效能提升 20%”等是原案例叙述，需要了解测量周期、基线、客观环境和统计口径，不能直接推断新客户也会达到相同结果。

## 8. P1：从离线评测到上线迭代的闭环

建议顺序是：固定数据的离线评测→真实接口沙箱→小范围影子运行→经授权的有限真实执行→持续监控。影子运行指系统生成结果但不直接替代原流程，便于比较；是否适用取决于客户数据和流程允许的方式。

每次版本更新都要保留模型、Prompt、工具 Schema、业务规则和知识索引的版本关联。发生严重问题时，回滚某个组件之前判断数据与状态兼容性，不能假设“回滚 Prompt”会撤销已派发任务。外部动作的纠正要走业务补偿或撤销流程。

失败复盘用“输入→证据→决策→执行→结果”组织。把有代表性的失败加入回归集，再检验修复没有破坏原有能力。这正好对应 JD 的资产沉淀要求：标准问答、Demo、POC 模板之外，**评测集、错误分类和验收口径也应成为售前资产**。

## 9. P0：30 秒客户解释、练习与自测

**30 秒解释：**“我们会先和您定义什么算成功，再用代表性案例验证。问答看证据是否正确，办事看业务系统是否真的达到目标状态，同时记录错误、耗时和成本。POC 报告会说明测试范围和未解决问题，后续用同一批关键案例检查每次升级有没有退步。”

**20 分钟练习：**选“道路补扫建议”，写 6 个案例：常规成功、道路歧义、数据过期、权限不足、资源冲突、提交超时。为每个写一条允许结果和一条硬性失败。再假设每个案例跑 3 次，在纸上模拟结果，并分别算“按尝试通过率”和“每次都通过的案例比例”。不要实际写生产工单。

**自测 1：**“准确率 95% 足够了吗？” **答案：**要先问任务、样本、分母、错误后果、重复运行和验收口径。5% 若包含越权派单，就不能只看平均值。

**自测 2：**“Agent 说任务完成，可以作验收依据吗？” **答案：**不够。要验证业务系统后置状态和必要回执。

**自测 3：**“使用更便宜的模型就一定更省吗？” **答案：**未必。多次重试、更长上下文、额外工具与人工返工可能让每个合格任务更贵。
