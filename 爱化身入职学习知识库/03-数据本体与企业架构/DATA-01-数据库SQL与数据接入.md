> 面对客户的 Excel、业务系统和传感器数据，能解释如何接入、如何关联、什么时候可信，并写出一条不会把工单统计翻倍的 SQL。P0 读第 1—4 节及自测，约 20 分钟；P1 再读余下内容。所有环卫数据、规则和阈值均为教学模拟，不代表爱化身产品接口或真实客户标准。

## 1. P0：先问数据代表什么，再问放在哪

售前最常见的错误是听到“有数据中台”，就默认可以让 Agent 直接分析。数据中台可能存有数百张表，但没有道路唯一编码、合同版本或完整历史。**能连上数据库，只证明网络和账号可用；业务可用还需要身份、语义、时间和权限都正确。**

模拟任务：“找出今天高风险道路，并为异常生成整改工单。”至少需要六类对象：道路 `RoadSegment`、巡检 `Inspection`、工单 `WorkOrder`、车辆 `Vehicle`、班组 `Team`、合同 `Contract`。客户说的“道路”可能是整条道路，而合同考核的是道路中某一责任段。必须先确定记录粒度：`RoadSegment` 一行是一段有起终点和方向的责任路段；`Inspection` 一行是一次巡检观察；`WorkOrder` 一行是一次独立整改任务。粒度不同的数据不能直接相加。

| 要素 | 教学例子 | 不澄清会怎样 |
|---|---|---|
| 主键 | 路段 `R-017`，工单 `WO-101` | 同名道路被误合并 |
| 外键 | 工单的 `road_id` 指向路段 | 无法追溯工单属于哪里 |
| 事件时间 | 巡检实际发生在 09:00 | 把 10:00 补传当作刚发现 |
| 处理时间 | 系统 10:00 收到巡检 | 无法发现采集延迟 |
| 有效期 | 合同规则 9 月 1 日生效 | 用新规则判罚旧作业 |
| 权限范围 | 甲项目只能看本项目 | 图谱、向量检索也可能泄漏 |

主键要求在约定范围内唯一、稳定、非空；手机号、车牌、道路名可能变化，不宜无条件充当永久身份。可用内部稳定 ID，并保留源系统 ID 与有效期。数据库中的 NULL 表示缺失或未知，不能自动等于零：车辆“剩余水量未知”与“水量为零”会触发不同调度决策。

## 2. P0：五类存储各自解决什么问题

关系数据库擅长明确结构、事务和关联查询，例如合同、班组和工单。对象存储放图片、音频和 PDF，数据库保存其地址、哈希和访问策略；把所有图片塞进工单表通常增加备份与传输负担。时序存储适合大量带时间戳的轨迹、速度、油耗，重点是时间窗口和聚合。向量索引用于相似语义候选召回，不负责证明余额、工单数量等精确事实。图存储擅长表达及遍历关系，但不是每一个 JOIN 都需要迁移到图数据库。

统一语义不要求物理上只有一种数据库。一个道路对象可以关联关系表里的责任单位、对象存储里的照片、时序系统里的轨迹和知识库里的合同条款。售前应该说明“对调用者提供一致的对象与权限”，而不是承诺“把所有数据向量化后就能自动统一”。同为“清扫”，合同要求的作业频次和司机填报的完成次数，仍需要业务口径映射。

公司介绍第 15—16 页将结构化、非结构化、时序、向量和知识图谱等纳入 Data OS 的能力表达；这支持讨论统一底座，但具体支持哪些数据库版本、增量机制、连接器和性能上限必须取得内部材料验证。见 [[数据架构来源]]。

## 3. P0：能读懂这条 SQL，就能避免大量售前事故

下面查询每条路段当前未关闭、已逾期的工单数。`:as_of` 固定为本次查询的当前时间；若要回看过去，需取得当时有效的工单版本或事件快照，不能拿今天的状态直接替换一个过去时间。`:project_id` 和 `:as_of` 是后端驱动绑定的参数占位说明，实际占位语法依所用驱动调整；不是让模型拼接 SQL 字符串。

```sql
SELECT r.road_id, r.name,
       COUNT(w.work_order_id) AS overdue_count
FROM road_segment AS r
LEFT JOIN work_order AS w
  ON w.road_id = r.road_id
 AND w.project_id = r.project_id
 AND w.status NOT IN ('closed', 'cancelled')
 AND w.due_at < :as_of
WHERE r.project_id = :project_id
GROUP BY r.road_id, r.name;
```

逐句理解：`LEFT JOIN` 保留没有逾期工单的道路；匹配条件限定同一项目，并筛选状态及截止时间；`COUNT(w.work_order_id)` 只数匹配工单，零工单得到 0。若使用 `COUNT(*)`，没有匹配工单的道路仍有一行占位，会被数成 1。若把 `w.status` 条件搬到 `WHERE`，空值行通常被滤掉，原本想保留的零工单道路会消失。[JOIN 的官方解释](https://www.postgresql.org/docs/current/tutorial-join.html) 状态或截止时间缺失的工单不会通过这些条件，应另外展示“无法判断数量”；否则逾期数为 0 容易被误读为全部正常。草稿是否纳入履约统计也应由业务口径决定，本例假定表中有截止时间的非关闭、非取消任务均在统计范围。

再考虑：`WO-101` 有两条巡检记录。把工单表与巡检表 JOIN 后再 COUNT 工单，`WO-101` 可能被数两次。正确办法是先把巡检聚合到所需粒度，或用 `EXISTS` 判断是否存在符合条件的巡检。`COUNT(DISTINCT work_order_id)` 可解决某些计数，但不是万能补丁；它掩盖不了金额、耗时等字段被重复求和。

统计“完成率”还要定义分母：今天创建的工单、今天到期的工单、今天实际完成的工单，是三个不同队列。推荐先定义“今天到期且未取消的工单中，在期限前关闭的比例”，再写 SQL，确认补录和跨天工单如何处理。准确表达业务口径比背 SQL 语法更能体现岗位价值。

## 4. P0：最小数据接入闭环

第一步拿一个脱敏样本，检查字段含义和记录粒度。第二步保留源数据副本与批次 ID，避免清洗后失去证据。第三步验证必填字段、唯一性、外键、枚举、时间和单位。第四步映射到统一对象 ID。第五步建立可查询视图。第六步将查询结果与客户人工台账对账。第七步显示更新时间、缺失范围和异常队列。

例如导入 100 条工单，其中 5 条道路 ID 缺失、3 条重复上传。不能宣称“已接入 100 条、成功率 100%”。可以报告“源记录 100 条；识别重复 3 条；待补映射 5 条；暂按两类不重叠计算，可进入业务验证的独立记录 92 条”。生产中要先明确缺陷集合有无重叠，再计算净数量。

> [!tip] 数据验收应当抽样到业务对象
> 随机选 10 条工单，从原系统、映射规则、统一对象直到前端逐项追踪。再定向抽取跨项目同名道路、撤销工单、补传巡检、合同换版等边界样本。只验证总行数一致，无法证明关联关系正确。

## 5. P1：批量、轮询、CDC、事件该怎么选

CSV/Excel 最快，适合前期概念验证，但需要明确更新方式及人工导入责任。API 轮询可以按 `updated_at` 增量获取，难点在分页、时间边界、重复记录、删除记录和接口限流。最好用游标或组合水位 `updated_at + id`，保留重叠窗口并幂等合并；仅请求“时间大于上次最大值”可能漏掉同一时刻的记录。

CDC 读取数据库变更日志，可持续捕获新增、修改、删除；它通常需要复制权限、初始快照与断点管理。以 Debezium 的 PostgreSQL 连接器为例，连接器从快照建立初始视图，再消费日志变化。它不是对任意老旧系统都能零改造启用的魔法；要核对数据库版本、日志保留、网络、恢复位置和源端负载。[Debezium 官方机制](https://debezium.io/documentation/reference/stable/connectors/postgresql.html)

业务事件比表级变化更接近业务含义：`WorkOrderApproved` 明确表示审批通过；“某行 status 从 2 变成 3”需依赖版本化解释才能理解。CDC 是数据变化获取方式，业务事件是语义契约，两者可以结合，但不能画等号。

实时性也需拆开：源端采集延迟 + 传输延迟 + 处理延迟 + 索引刷新延迟 + 查询延迟。API 返回 1 秒，不表示车辆位置只落后 1 秒。应在画面上呈现“状态截至 10:02；当前位置可能延迟 2 分钟”，超过模拟阈值就禁止自动派车、转人工确认。不要用全链路“实时”掩盖各段延迟。

## 6. P1：事务、索引和读写隔离的售前意义

如果创建工单成功而占用车辆失败，会出现无人承接任务；同一数据库内可用事务使这些更新一起提交或撤销。事务不自动覆盖外部短信、车辆平台或第三方接口；这些需要 [[DATA-04-企业集成权限部署与可靠执行]] 的幂等、补偿和对账。[PostgreSQL 事务说明](https://www.postgresql.org/docs/current/tutorial-transactions.html)

索引帮助缩小查找范围，但增加写入成本和存储占用。对于按项目、状态、截止时间查询的工单，应基于真实查询模式与数据分布评估索引；不是每个字段都建一个。`EXPLAIN` 用于看执行计划，`EXPLAIN ANALYZE` 会实际执行查询，不能随手拿有副作用的语句到生产验证。[官方 EXPLAIN 说明](https://www.postgresql.org/docs/current/using-explain.html) 售前对性能的贡献，是补齐数据量、并发数、查询形状、P95 延迟目标和测试环境，再交由工程同事确认方案。

Text-to-SQL 场景通常从只读账号、允许表/视图、行级权限、查询超时和结果行数限制起步；验证 AST 或使用受控查询模板可缩小风险。前端隐藏跨项目按钮并不是权限控制；数据库或服务端仍需独立限制范围。对写入动作，应通过有业务校验的 API 执行，而不是让模型直接生成 UPDATE。

## 7. 十分钟演练与参考答案

**练习：** 客户给出两张表：道路表有 10 条路段；工单表有 30 行，其中 2 行重复、3 行道路名相同但属于不同区、1 行缺少截止时间。你承诺明天展示“实时履约预警”，有哪些问题必须今天解决？

**参考答案：** 先确认工单唯一键并去重，建立区/项目与道路 ID 映射，不按道路名称直接 JOIN；缺失截止时间标为“无法判定”，不当作未逾期；确认真实源系统更新时间，若只拿静态表则演示批次时间并称为模拟预警；与客户固定合同口径及逾期计算方法；用异常样本检查结果；明确写回接口未接通时只能创建模拟工单。

**自测 1：** 数据已经进入向量库，能精确统计 2026 年 8 月逾期率吗？

**答案：** 向量相似召回不保证遍历全部工单，也不承担精确聚合。应在受权限控制的结构化数据上确定口径并计算，向量检索可辅助找到规则文档。

**自测 2：** 为什么“没有巡检记录”不等于“未清扫”？

**答案：** 可能未采集、离线补传、映射失败或源端丢失。可以输出“缺少清扫证据”，若要判定未清扫，必须说明证据规则和数据覆盖条件。

**自测 3：** 什么是你入职前必须会、可以入职后再深入的？

**答案：** 必须会识别主外键、粒度、JOIN 重复、NULL、时间和最小接入流程；不必五天内成为数据库调优或 CDC 集群运维专家。遇到日志权限、亿级轨迹、跨库一致性要求，应带着准确条件协同 FDE/研发。

## 8. 30 秒客户话术

“我们先选一个能验收的环卫场景，把道路、工单、巡检和合同口径对齐，再接入必要数据。接通只是第一步，我们还会核对唯一编码、更新延迟和权限，并和您现有台账对账。这样演示的不只是一个看板，而是一条能说明数据从哪里来、结果怎么算、哪些记录还不能判断的业务链路。”
