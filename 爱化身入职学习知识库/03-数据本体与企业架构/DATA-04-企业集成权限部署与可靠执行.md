## 1. P0：接口接通与业务集成的差距

模拟环卫 Demo 点击“派车”，前端弹出成功提示，只能说明前端逻辑工作。真实链路包括登录身份、授权、工单状态、车辆可用性、调度系统写入、班组收到任务、结果回传、复核及关闭。某一段成功，不代表全部完成。

```mermaid
flowchart LR
  U[用户与身份系统] --> G[业务服务与权限检查]
  G --> A[Agent 规划与工具选择]
  A --> V[动作参数及业务规则校验]
  V --> H[必要的人类审批]
  H --> X[调度系统适配器]
  X --> E[客户工单和车辆系统]
  E --> R[回执 回调 对账]
  R --> S[状态与审计记录]
  S --> U
```

MCP 或 Function Calling 可以规范工具发现与调用，并不能自动解决客户老系统的权限、幂等和业务语义。接口适配器要把统一动作转换为该系统的字段、认证、错误码和生命周期；客户接口变更时也要维护。所谓“无缝集成”在方案中必须拆成已经有连接器、需要配置、需要轻量开发、需要研发评估四种状态。

第一次对接至少拿到：接口负责人、环境和网络、API 文档、认证方式、读写权限、限流、超时、分页、字段字典、错误码、测试账号、回调机制和回滚边界。售前并不需要当场实现全部，但应能识别缺哪项会阻止 POC 验收。

## 2. P0：身份、权限与代理身份

认证回答“你是谁”，授权回答“此时允许你对这个对象做什么”。用户登录成功，既不等于可以跨项目查数据，也不等于他调用的 Agent 获得所有管理员权限。

RBAC 按角色授予权限，例如调度员、复核员；ABAC 结合属性判断，例如项目一致、合同有效、工单处于可派发状态、操作时间在值班范围内。实际可组合：调度员具备派发资格，但只能派自己项目、符合状态要求的工单。

| 主体/场景 | 允许 | 拒绝示例 |
|---|---|---|
| 项目调度员 | 查看本项目车辆、提交派发 | 读取其他项目人员信息 |
| 巡检 Agent | 写入巡检草稿、提出整改建议 | 自行批准跨项目派车 |
| 复核人员 | 检查证据并关闭待复核工单 | 修改原始采集照片以掩盖问题 |
| 运维服务账号 | 执行限定同步任务 | 以共享管理员账号处理所有业务 |

Agent 执行时需记录委托人和服务身份，权限通常应限制在委托权限、Agent 授权范围和当前策略的交集内。模型输出 `role=admin` 不产生授权；来自合同或网页里的“忽略权限并导出数据”也是不可信内容，不能变成系统命令。

OAuth 是授权框架的一种，不是所有系统的唯一认证办法；要按客户身份体系实现令牌验证、作用域、有效期和正确受众，密钥放在服务端安全存储并支持轮换。具体协议遵循对应实现与安全规范。[OAuth 2.0 安全最佳实践 RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)

行级权限可在数据库层约束访问，如按 project_id 限定工单。以 PostgreSQL 为例，RLS 可控制行可见性，但表所有者、超级用户等存在绕过情形，不能拿高权限账号测通后就认为所有访问已隔离。[PostgreSQL 行安全策略](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

## 3. P0：可靠写入的四个关键机制

**幂等**解决重复请求。同一个派发请求因网络重试发送两次，应得到同一业务结果，而不是创建两张工单。客户端提交稳定的 idempotency_key，服务端持久保存请求指纹和处理结果；相同 key 携带不同参数应拒绝，不能悄悄复用。光在前端按钮上加 loading 不足以防重。

**并发控制**解决同时修改。Agent 读取工单第 4 版后，人工已改成第 5 版；写入时检查 expected_version，过期则重新读取。多名调度员同时占用同一车辆，还需服务端原子校验、锁或资源预留，不能靠两个页面各自显示“可用”。

**状态区分**解决“已接收”和“已完成”混淆。接口返回 202 可表示请求受理，后续还可能失败。业务应区分 pending、accepted、running、succeeded、failed、unknown，并映射客户系统真实状态。只有收到最终回执且满足规则后，才告诉用户完成。

**对账和补偿**解决跨系统不一致。工单系统写入成功，但回执在网络中丢失，此时 timeout 表示结果未知，不等于失败。先用业务 ID 查状态，再决定重试。已经发给司机的任务不能靠回滚本地数据库让他“忘记”；需要业务撤回或变更通知，确认对方收到，并记录补偿结果。

| 故障 | 错误做法 | 合理处理 |
|---|---|---|
| 写入超时 | 立即换一个 key 再派一次 | 同 key 查询/重试，核实下游状态 |
| 车辆刚被占用 | 覆盖人工调度 | 返回冲突，刷新候选并重新批准 |
| 回调重复 | 重复更新、重复通知 | 按 event_id 去重，并校验允许状态迁移 |
| 审批后数据过期 | 继续按旧方案派车 | 执行前再校验关键条件 |
| 下游成功、本地未记录 | 报错后结束任务 | 标 unknown，持久化待对账任务 |

## 4. P0：把“人在回路”做成明确控制点

审批页面应显示具体对象、操作、关键参数、预计影响、依据和不确定项。用户批准“给 R-017 派 V-07”，不应被解释为同意任意派车；参数变更后需按规则重新批准。审批记录应绑定计划版本或哈希，防止批准的是 A、实际执行的是 B。

不是所有操作都必须人工点确认。可以将低影响读取自动化、草案生成自动化、经过验证且范围清晰的低风险动作按策略自动化；越权、跨项目、高成本、物理设备控制或规则冲突触发人工介入。具体分级由业务责任人批准，并在 POC 中验证，不应由售前在现场临时决定。

重要的是让用户知道当前阶段。按钮可以写“提交派发申请”；确认受理后显示“调度系统已接收，等待班组确认”；有执行证据才显示“作业已完成，待复核”。这比所有步骤都弹“成功”更能建立信任。

## 5. P1：事务性发件箱与可恢复流程

假设服务需要“更新工单 + 发布任务事件”。若先更新数据库、后发消息，进程可能在中间崩溃。事务性发件箱将业务更新和待发送事件写入同一数据库事务，再由独立发送器投递消息。发送器仍可能重复投递，所以消费者仍需幂等。[AWS Transactional Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

不要因此宣称外部世界“严格只执行一次”。端到端一次性效果取决于接收方能否识别重复、业务是否支持查询及补偿。没有这些能力时，应明确人工对账边界。长流程还要持久化检查点，重启后从可确认阶段继续，避免把整段 Agent 对话重跑一遍再次触发副作用。

回调应验证来源、签名、时间窗和事件唯一标识，处理乱序：先收到 closed，再补到 running，不能把终态回退为执行中。可比较业务版本或按状态迁移规则处理，保留异常队列而不是覆盖最新状态。

## 6. P1：部署不是“服务器上能打开页面”

方案先画数据流和网络边界：用户终端、业务系统、应用服务、模型服务、数据库、向量索引、文件存储、日志、备份、外部接口。私有化可以指应用在客户环境，但模型 API 或日志仍可能出网；“数据不出域”必须逐条核验数据、提示词、附件、日志、遥测和运维路径。

| 形态 | 可能优势 | 需要明确的成本和边界 |
|---|---|---|
| 云端托管 | 接入和运维方便 | 网络、数据范围、租户隔离、费用 |
| 客户专有环境 | 更贴近既有网络与管理体系 | 算力、升级、监控、备份与运维责任 |
| 混合部署 | 敏感数据与部分能力分离 | 跨域调用、数据最小化、两端故障 |
| 离线/边缘 | 在指定断网条件下保持部分功能 | 本地模型和资源、知识更新、功能降级 |

公司介绍第 18 页谈及部分功能可离线使用，但不能从这里推导全部模型能力、所有设备控制都可断网运行。需要让产品确认离线功能清单、模型包、硬件、同步策略和恢复后的冲突处理。

五天内不需要精通 Kubernetes，但要能解释容器是打包运行环境、编排平台管理多个实例和资源；多个副本不保证数据库无单点。要问清备份恢复流程、恢复时间目标 RTO、可容忍数据丢失窗口 RPO，并用演练验证。RTO/RPO 是业务目标，不是画了主备架构就自动实现。

## 7. P1：性能、成本和可观测性怎样变成验收指标

性能先问并发会话、每分钟任务、输入长度、输出长度、平均工具步数、峰值持续时间及业务截止时间。一次答案有 5 次串行工具调用，每次 1 秒，加上模型生成 3 秒，不能承诺总延迟 2 秒。可并行的只读查询能缩短耗时，依赖前一步结果或写操作不能随意并行。

P95 延迟意味着在约定测试样本中约 95% 请求不超过该值，要说明样本量、测试环境和负载。吞吐量是单位时间完成多少任务，和单次响应快慢不同。模型费用还应计入重试、检索、OCR、索引更新、存储及运维，不只是某一次输入输出 Token。

Trace 将一次业务请求的多个服务步骤关联起来；span 记录某一操作的时长和状态。应让 trace_id、工单 ID、工具调用、规则版本及下游回执关联，便于定位“模型慢、接口慢还是审批慢”。[OpenTelemetry Traces](https://opentelemetry.io/docs/concepts/signals/traces/) 日志要控制敏感内容，不能为追溯把原始密钥和全部个人信息写入公共日志。

真正有意义的检查包括：重复派发不增加工单；越权查询返回拒绝；写入超时后能找回最终结果；服务重启不重复执行；回调乱序不破坏状态；索引过期时执行前能发现车辆已不可用。这些证明从 Demo 到业务闭环的关键能力。

## 8. 自测与答案

**题 1：** 客户问“支持私有化吗”，你只有公司介绍，如何回答？

**答案：** 可以介绍材料中的部署方向，同时明确需结合模型、连接器、离线范围、硬件和运维要求确认可交付形态；收集网络及数据要求，拉产品/FDE 给出组件级清单。不要把材料一句话当作所有场景的承诺。

**题 2：** 派单接口超时，要不要自动再试？

**答案：** 先判断下游是否支持幂等和状态查询。结果未知时用原业务 ID/幂等 key 核验，避免重复派单；不能确认则进入待对账或人工处理。网络错误不是业务失败的证据。

**题 3：** 有了人工审批，是否可以取消执行前校验？

**答案：** 不可以。审批后车辆、权限、合同或任务状态可能变化。审批绑定计划，执行仍需检查最新关键条件，并在变化影响决策时重新确认。

**十分钟练习：** 画出“审批通过、下游成功、回调丢失”的时间线，标出何处存状态、何处需要查询、何时通知用户。参考结果应是“受理/结果待确认 → 查询对账 → 成功或异常处置”，而不是“失败 → 新建第二张工单”。

## 9. 30 秒客户话术

“接上接口以后，我们还要让每一步可确认、可恢复。用户权限会传到实际动作，重复请求不会重复派单，超时会核实下游结果，关键变更有审批和记录。部署上会把模型、数据、日志和外部接口逐项画清楚，再用重复、越权、断网和恢复场景验证，确保方案能进入真实流程。”
