> [!important] 怎么学
> **P0：第 1—5 节，约 25 分钟；P1：第 6—9 节。**这篇要把你“能很快做出来”的优势升级成“能明确证明什么、出问题也能解释”的能力。全部环卫样本、工期和阈值均为教学设计；客户项目需要双方确认。

## 1. 四种活动回答四种问题

| 活动 | 核心问题 | 输入 | 输出 | 不足以证明 |
|---|---|---|---|---|
| Demo 演示 | 这种工作方式是什么样？ | 场景脚本、可展示样例 | 可理解的业务体验、进一步兴趣 | 生产稳定性和普遍业务收益 |
| 原型 Prototype | 交互或技术路径能否初步实现？ | 最小任务、界面与接口假设 | 可交互版本、主要未知 | 全量集成、长期维护 |
| Workshop 工作坊 | 各方对流程和验证目标是否一致？ | 业务人、IT、样本、当前流程 | 范围、对象、规则、指标和责任人 | 单靠开会证明效果 |
| POC 概念验证 | 哪个关键假设在约定条件下成立？ | 验证章程、样本、基线、受控环境 | 证据、失败分析、继续/停止决策 | 自动等同正式上线验收 |

试点 Pilot 通常进一步进入有限真实工作环境，验证采用、集成、运维和持续结果。名称在不同公司不完全统一，开工前约定含义更重要。AWS 的官方讨论把 POC 放在解决业务问题、降低不确定性与走向部署的路径上，而不是只展示技术新奇。[AWS：从 POC 走向生产](https://aws.amazon.com/blogs/enterprise-strategy/generative-ai-getting-proofs-of-concept-to-production/)

JD 的“原则上半天内概念原型、当天演示版本”，应理解为快速完成范围明确的演示任务。它不意味着半天部署完整 Data OS，更不意味着生产鉴权、客户数据治理、写接口审批、运行保障和验收已经完成。你可以用轻量服务表达公司架构的业务效果，但要标明“概念原型，当前未使用真实 Agentrix 环境”；没有调用产品就不能写“Agentrix 实测”。

## 2. 半天 Demo 的方法：做一条完整链路，减少横向功能

选择主任务：“根据一条道路垃圾事件，给出有依据的班组建议，主管批准后在演示工单服务中创建任务，并显示回执。”观众能看见一件事情的前后变化，往往比看到十个菜单更容易理解价值。

建议按四小时教学时间盒分配：30 分钟固定角色、场景和要证明的三点；45 分钟整理脱敏样本和对象映射；90 分钟完成界面、查询和模拟写接口；45 分钟检查正常与失败路径；30 分钟录制备份、核对演示声明和排练。这个分配不是对实际研发耗时的承诺；如果接口或产品环境未就绪，就缩小演示范围或明确改用样例。

**最小画面必须包含业务证据。**左侧事件卡展示事件来源和时间；中间地图展示道路与责任区；右侧建议卡列出班组、依据、数据更新时间和不确定项；底部显示“待主管确认 → 创建中 → 已返回工单号”。大段会动的“思考过程”不能替代来源和回执，展示可记录的操作步骤即可，不需要声称能展示模型全部内部推理。

**最小对象集：**道路段、事件、班组、班次、工单，外加道路—班组责任映射。只读数据和写操作分开；写操作仅发往演示服务或已授权沙箱。演示环境默认用脱敏或合成数据；预置记录保留来源、采集时间、适用范围。数据名称“真实”不代表今天仍准确，更不代表可以向任何客户展示。

**最低工程检查：**应用可启动；环境变量不进入前端；输入参数有结构校验；超时可见；重复点击不重复创建；错误不显示密钥；每次调用能追踪；刷新后的状态解释一致。无需给四小时原型堆砌所有企业能力，但要识别哪些尚未实现并写入能力卡。

## 3. 演示的三层证据和故障应对

现场要清楚标注三类材料：实时调用、预置数据驱动的交互、录屏/回放。界面用小标签标识；开场用一句话说明：“今天的路段和班组是演示样例；查询和审批在现场执行，工单写入演示服务，不影响真实作业。”若用了历史真实数据，则说明来源已获准展示、数据日期及脱敏范围。

你的面试中，实时 POI 获取出现异常，面试官允许继续。这说明一次不稳定并不抹去能力证据；但面向客户需要更成熟的处置：先保护业务叙事，再定位问题，不在台上无边界调试。

可预设一次短重试，仍失败就说：“本次调用未返回可用结果，当前不能判断是配额、网络还是服务错误。我切到已标注时间的预置样例，继续说明后续流程；实时链路的错误日志会纳入验证清单。”只有日志已证明配额限制，才能说是配额问题。不要说“之前都没问题”，也不要暗中用回放冒充成功实时调用。

| 情况 | 现场动作 | 保留的可信度 |
|---|---|---|
| 读接口超时 | 显示失败；切显式预置数据 | 分清第三方依赖与后续业务流程 |
| 模型给错班组 | 展示拦截/人工修正并记录 | 证明有纠错设计；不能把错结果算成功 |
| 写接口无回执 | 显示状态未知；按幂等键查询 | 避免盲目重试造成重复工单 |
| 页面崩溃 | 切录屏并明确说明 | 保存演示目标，保留故障证据 |
| 客户临时要求跨区自动派单 | 先说明现有演示范围 | 将新场景记为待验证，避免现场承诺 |

## 4. 工作坊不是听需求，是共同完成验证设计

一个 90 分钟的教学议程：10 分钟确认业务结果与边界；20 分钟复盘一笔真实任务；20 分钟画对象、关系和状态；15 分钟走异常与权限；15 分钟定样本与验收；10 分钟锁定责任人与下一步。最好让业务负责人、实际使用人、IT/数据负责人都在场；缺席造成的未知要明记，不能由售前代替客户拍板。

桌面推演用三张事件卡即可：正常责任区、有位置但合同映射缺失、班组已下班。依次问系统知道什么、能做什么、谁确认、失败怎么处理。特别观察业务方有没有相互矛盾的规则：运营说“距离最近即可”，区域经理说“不允许跨合同”；这类矛盾在写代码前被发现，就已经产生工作坊价值。

输出应在会议中复述：问题定义、目标用户、现状图、目标状态图、对象清单、数据缺口、POC 范围、验收草案和责任人。不要把所有想法都塞入本轮范围；新增想法单列待选池，并标明取舍理由。

## 5. POC 章程：让结论可判断，也能坦然判失败

一个好假设是：“在已完成道路和班组映射的指定区域，系统对日间常见道路垃圾事件，能提出符合责任区与班次规则的班组建议，业务人员能检查依据，审批后在沙箱仅创建一张工单。”它没有混入无人车控制、全市资源优化和现场作业完成率。

章程至少写：业务目标、待验证假设、对象与接口范围、明确排除项、样本来源、基线、指标计算、硬性失败条件、时间与投入、双方责任、变更机制和结束决策。入场条件没满足，不应假装 POC 已开始。例如没有测试账号时可以完成原型，但无法宣称已验证真实鉴权集成。

验收要区分三层：**业务任务正确性**（派给合格班组，依据有效）；**流程完整性**（审批、唯一建单、状态回读）；**工程条件**（权限、时延、成本和审计）。语言流畅不能抵消越权写入。测试集内发生一次越权应按约定硬门槛处理，不能混进平均“正确率”稀释。

## 6. P1：样本、基线和指标如何设计才不自欺

教学样本可暂定 50 个独立事件：正常 30、缺失数据 8、跨区/班次异常 6、重复或更新冲突 6。它仅演示分层思路，样本量不是统计充分性的保证。另建权限攻击、超时、重复点击、写入回执丢失等专项测试。冻结验收样本，不用同一批样本反复调提示词后再宣布泛化成功；开发集、验收集及版本都要留档。

若 45/50 个事件成功，应该报告“这一验收集成功 45 个，失败 5 个”，同时列失败类别和样本组成。小样本不足以精确推断全域真实成功率，也不能把 100 次调用当成 100 个独立场景。

| 指标 | 明确定义 | 常见误读 |
|---|---|---|
| 任务成功率 | 满足该事件全部必要条件的事件数/适用事件数 | 只看最终回答文本是否漂亮 |
| 合规拒绝正确性 | 不可操作事件是否正确拒绝/升级 | 一律拒绝得到“零错误” |
| 引用可核查率 | 正确引用对象、规则、版本的回答占比 | 有链接就算依据正确 |
| 建单一致性 | 已批准请求是否形成且只形成一张对应工单 | HTTP 200 就算闭环 |
| 端到端耗时 | 用户提交至约定终点的耗时分布 | 用模型首字延迟代表业务耗时 |
| 每成功任务成本 | 同期全部执行成本/成功任务数 | 只算成功调用，忽略失败重试 |

适用任务集合和排除规则要在验收前冻结，不能在模型失败后把难题移出分母。正常任务成功率与异常正确处置率分别报告，再按约定呈现总体结果；若成功数为零，每成功任务成本不能计算成零，应报告“无成功任务，单位成功成本不可计算”并列实际总支出。

基线选择原人工流程或当前系统处理同类任务。记录操作时间和等待时间；条件允许时采用同一时期可比任务或交叉分配，避免把雨天复杂事件和晴天简单事件比较。人工评审先写评分量表，最好由业务专家检查争议样本；模型评分可辅助，不应独自判定派单与执行是否正确。

## 7. P1：方案越简单，越容易找到真实增量

先做无模型基线：按合同范围和班次过滤班组，再按简单规则排序。若这已解决 80% 的任务，就把 LLM 用在口语澄清、信息解释和复杂异常，而不是让它重写确定规则。是否使用 Agent 动态规划，取决于任务分支是否开放以及验证是否显示收益。Anthropic 的官方方法也建议从满足任务的简单方案开始，复杂 Agent 常伴随更多时延、成本与错误累积；这里引用的是架构判断原则，不是推荐其当前具体产品。[Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

补货场景同理：先比较“最低库存阈值规则”与“加入订单/在途量的规则”，再评估预测方法是否有额外收益。多 Agent 在界面上看起来热闹，不能作为价值增量。

## 8. P1：POC 结束不是默认上线

结束报告写清通过项、失败项、未测项和适用条件。建议三类结论：继续到受控试点；补齐某项依赖后重测；当前不值得继续。通过的 POC 仍需生产部署设计、身份权限、监控告警、值守与故障处理、数据更新、容量评估和交付验收。未测试的产品能力保持“未验证”。

失败也能形成好交付：例如模型建议足够准确，但客户没有可调用的派单接口。结论不是“AI 做不了”，而是“当前只能验证建议层，执行闭环依赖接口建设或获批的替代集成方案”。这会直接改变预算、排期与商业路径，应移交 FDE 评估而不是售前私下兜底。

## 9. 有答案自测

1. 用录屏兜底是否不专业？**答：**明确标注的录屏是正常演示资产；把录屏说成实时成功才会破坏证据可信度。
2. 50 个样本全通过，可以说生产零幻觉吗？**答：**不可以。只证明特定版本在特定样本和条件下通过；生产分布、权限、外部系统与规模仍可能不同。
3. POC 的首要任务是尽可能展示所有产品能力吗？**答：**应验证影响继续投资的关键假设，范围越广越容易失去可判定性。
4. 工单请求超时后是否立即重发？**答：**先判断服务端可能已成功，利用请求幂等标识和状态查询确认；没有这类机制须暴露不确定状态并人工处置。
5. 你能写一个半天原型，是否需要熟悉整个生产技术栈才有价值？**答：**不需要一次掌握所有细节，但必须识别当前未解决的生产条件并找到负责人。

练习：用 [[TPL-02-POC章程与验收矩阵]] 填一轮验证，不写代码。只有当你能判定正常、异常、失败各是什么，才开始搭界面。来源与范围见 [[售前方法来源]]。
