> [!important] 学习目标
> **P0：第 1—4 节，约 20 分钟；P1：第 5—9 节。**能写出一页让客户作决策的方案；能回答“为什么值得做、为什么用这个架构、为什么现在不能承诺”。本页所有金额、工时、效益与阈值均为教学假设，不是爱化身报价、交付实绩或客户预算。

## 1. 方案不是能力清单，是带证据的选择建议

方案的逻辑应该是：客户要改善什么结果；为什么当前流程达不到；建议改变哪个环节；产品和实施如何支撑；验证什么；付出哪些成本、承担什么条件；下一步决策是什么。客户不需要先学完 Agentrix 的所有名词才能判断价值。

一页方案可以写成以下六段：

1. **业务目标：**缩短道路事件从发现到有效派单的等待，保留可追溯依据；负责人为区域运营主管。
2. **现状与证据：**目前需要跨巡检、合同与班组系统核对；已知是人工步骤，具体耗时分布待日志和观察确认。
3. **首期范围：**一个责任区域、日间常见事件、建议加人工审批、沙箱建单与状态回读。
4. **方案结构：**对象与规则对齐提供依据；编排协调查询、校验、审批和工具调用；岗位界面供调度员操作。与 Agentrix 三层的映射是方案假设，具体产品实现需能力确认。
5. **成功标准：**任务正确性、异常正确升级、审批与唯一建单、耗时和每成功任务成本；目标由双方用基线确定。
6. **投入与下一步：**业务和 IT 提供样本与沙箱权限；售前形成验证包；复杂部署由 FDE 评估；POC 后决定试点、补测或停止。

这种写法也避免公司材料中的案例数字被复制到新客户：某客户“人车综合效能提升 20%”即便出现在公司介绍，也只是公司对该案例的表述。你尚不知道其统计口径、对照条件、验收主体和实施范围，不能写成“贵司一定提升 20%”。

## 2. 建立价值树：技术表现如何变成业务结果

价值链可以写为“对象映射更准确 → 少查错责任关系 → 建议更可用 → 调度员少做重复核对 → 有效派单更快 → 在资源和执行条件允许时改善整改结果”。每个箭头都有条件：如果班组本就满负荷，更快派单未必更快整改；如果人不采用建议，模型准确率不会自动变成收益。

| 层次 | 环卫例子 | 谁确认 | 不能跳过的条件 |
|---|---|---|---|
| 技术指标 | 责任映射正确、工具调用成功 | IT 与业务共同评审 | 数据及规则版本正确 |
| 任务指标 | 建议可用、审批后唯一建单 | 调度负责人 | 异常处理、审批流程可用 |
| 流程指标 | 人工处理时间、等待时间下降 | 运营负责人 | 用户采用、无新增返工 |
| 经营指标 | 加班支出下降、履约改善 | 经营/财务负责人 | 真实支付减少或容量变现 |

不要让一个技术指标承担所有目标。例如地图渲染快只是交互体验；车辆空驶率受调度算法、司机行为、路线约束与数据覆盖共同影响；行政处罚和投诉也有外部因素。把这些影响画清楚，才能回答“这一结果有多少可以归因于本项目”。AWS 的生产价值指南也将业务结果、运营需求、治理证据和系统健康看作不同利益相关方的评价维度。[AWS：持续交付生成式 AI 价值](https://docs.aws.amazon.com/prescriptive-guidance/latest/gen-ai-lifecycle-operational-excellence/prod-value.html)

## 3. 成本收益测算：先算清口径，再讨论漂亮数字

必须区分**理论时间释放、实际产能改善、现金节省、收入增加**。减少一名员工每天一小时重复工作，通常先产生时间释放；工资仍照常发，不能直接说省了一小时工资现金。若确实少付加班费、减少外包账单或避免新增招聘，才可能转为可确认的现金收益。收入增加应关注增量毛利/贡献而不是把营业额全算收益。

教学假设：月事件量 20,000；其中适用本方案的比例 60%；实际采用率 70%；每件适用且采用的任务，净人工操作时间由 6 分钟降至 3 分钟，后者已包含复核和返工。则：

```text
月采用任务量 = 20,000 × 60% × 70% = 8,400 件
月释放工时 = 8,400 × (6 - 3) ÷ 60 = 420 小时
若每小时完全成本按 60 元估算：容量价值 = 25,200 元/月
```

25,200 元只能叫容量价值估算，不自动进入现金 ROI。假设其中 40% 的工时最终通过减少已存在的可变加班/外包支出变现，则现金收益估算为 10,080 元/月；40% 必须由业务与财务证实，不可把它当行业默认值。若减少的外包支出已经由这 40% 计入，就不能再新增一条同样的“外包节省”。

教学成本假设：一次性实施 60,000 元；每月平台与运行 4,000 元、持续运维 2,000 元；每月合计 6,000 元。按全年都达到上述使用水平的简化假设：首年收益 120,960 元，首年成本 132,000 元，首年净收益 -11,040 元，首年 ROI 为 -8.4% 左右；稳定月净收益 4,080 元，简单回收期约 14.7 个月。实际还要加入爬坡期、税费、资金时间价值等适用条件，这个例子不提供投资建议，只训练报价讨论的口径。

```text
同期间 ROI = (同期间可归因收益 - 同期间总成本) / 同期间总成本
简单回收期 = 初始投入 / 稳态月净现金收益   （仅当月净收益为正且假设适用）
```

这个结果不必强行美化。可能需要扩大可复用规模、降低集成成本、寻找经核验的独立收益，或承认此场景暂不值得做。若全部时间都不能变现，现金收益可能接近零，但可讨论容量、服务质量或风险管理价值，并明确其非现金性质。

总成本至少涵盖：软件/平台许可、模型推理、检索与存储、数据接入与清洗、本体及规则配置、接口改造、部署资源、评估、运维、培训和用户迁移。模型调用成本还应计入失败、重试和回放评估；不能用一个成功问答的 token 花费推算整套平台价格。

## 4. 技术异议的回答结构：理解担忧，提出可检验答案

先判断对方担心效果、可靠性、控制权、预算还是重复建设。推荐四步：复述真正问题 → 给当前能确认的答案 → 说明适用条件与未知 → 提出证据或验证动作。不能用概念密度掩盖未知，也不需要当场猜一个产品参数。

| 客户问题 | 可直接练习的话术 | 后续证据 |
|---|---|---|
| 我们已经有知识库，为什么还需要？ | “先看它是否已满足业务。若只是找 SOP，现有知识库可能足够；若要把道路、合同、班组的实时状态对齐后派单，还需验证语义关系和受控动作链。” | 用同一任务比较现有方案和拟议方案 |
| 是不是套壳大模型？ | “价值应看数据语义、权限、工具、流程和可运营性是否解决你的任务。我们逐项展示证据，而不只比较底层模型名称。” | 能力清单、实际版本、任务测试 |
| 为什么不用纯 RAG？ | “RAG 适合带依据地回答资料问题；跨系统关联和办事还需要结构化查询、关系或规则、工具与审批。RAG 也能与这些能力组合，并非绝对做不到多跳。” | 相同样本的链路与错误分析 |
| 本体建了就不会幻觉？ | “本体能帮助统一对象和关系，但映射、数据、检索和模型都可能出错，需要约束与评估。” | 映射审查、引用检查、异常样本 |
| 可以全部自动执行？ | “先区分读取、建议、审批后写入和高影响动作。每类权限与失败恢复不同，本轮建议先验证受控闭环。” | 动作权限表、审批、幂等与回执 |
| 数据能不出域吗？ | “要以部署和数据流为准，确认模型、嵌入、日志、监控和外部工具的全部路径后给结论。” | 经确认的数据流图与配置 |
| 能保证毫秒级、99.99%吗？ | “需要确认测量对象、负载、依赖和保障范围。先给已测数据与测试条件，SLA 由正式方案与合同确认。” | 性能报告、运行架构、承诺主体 |
| 明天就能上线吗？ | “明天可争取交付已约定范围的演示；上线日期需要确认权限、接口、部署和验收条件。” | 依赖清单及 FDE 排期评估 |

## 5. P1：做公平比较，而不是做竞争对手的稻草人

不要拿本公司的完整平台对比竞争对手的单次聊天，也不要说“别家只能做问答”。以客户任务建立比较表，维度可以包括业务对象一致性、实时数据、动作回写、权限、可解释证据、部署方式、维护投入、扩展成本、上线周期。每项标“已验证/文档说明/待验证”，同时写适用版本和条件。

在单一文档查询场景，轻量 RAG 可能更快更便宜；在跨系统流程协同、多个岗位复用业务语义的场景，平台底座才可能体现额外价值。是否值得引入平台，要看可复用任务数量、现有系统成熟度、数据治理负担和长期运营资源。主动给出“现有系统足够”的结论，也能建立技术可信度。

公司介绍第 19 页强调 Agentrix 与现有大数据平台共生的定位，这可以作为公司叙事引用，但不能据此假设每个客户系统都无需改造。接口缺失、口径冲突、旧系统扩展限制仍可能产生建设成本。

## 6. P1：商业路径与技术范围一起设计

售前需要知道谁出钱、谁验收、谁使用、谁维护，以及 POC 通过后走什么流程。商业同事主导价格、采购与合同，你提供可交付的范围、依赖、估算依据和风险。不要凭面试中提到的大客户规模推断公司的正式最低合同门槛，也不要替公司承诺分成、合资、免费开发或永久维护。

环卫可用“单区域验证 → 有限区域试点 → 评估跨区域复用”作为建议路径，每一阶段都有进入条件。跨区域不是复制界面即可：合同、道路编码、班次、设备接口与考核规则可能不同。补货也一样，新增仓库可能共享 SKU 主数据，却需要新的库存语义、调拨规则和审批链。清楚解释复用项与变化项，才有可信的规模化故事。

## 7. P1：敏感性分析和归因，防止一个数字误导决策

把最不确定的输入列出来：适用比例、采用率、净节时、实际变现比例、一次性集成成本、月度维护成本。分别看保守、中性、乐观情景；不要所有变量同时取最好值而只展示一个 ROI。对于上述教学模型，若采用率减半，收益近似减半，而固定成本不会同比减半；这说明推动一线采用可能比再降一点 token 成本更关键。

归因时关注同期变化：是否同时换了班组、优化了排班、增配了车辆、改变了考核？观察到整改时效改善不等于全部由 AI 造成。可先选直接相关的处理时间作为本轮指标；对经营收益保留更长观察期及可比对照。避免同时计入“节省人力”“人效翻倍”“处理能力翻倍”三种描述对应的同一份增量。

## 8. P1：失败案例与现场纠偏

**失败：把“自动生成调拨单”讲成“无人审批补货”。**客户担心错单占用库存，项目停滞。纠偏是明确建议和实际库存操作的差别，演示人工审批、数量限制、重复防护和系统回执。公司介绍第 27 页本身就描述生成单据后进入人工确认，不能把宣传案例自行升级成无条件自治。

**失败：被问模型名后进入参数竞赛。**售前花十分钟讲模型大小，却没有解释为什么工单不会重复创建。纠偏是先回答已获准公开的模型与替换条件，再回到任务指标和系统控制；未知参数记入能力确认，不以猜测填空。

**失败：为了守住 ROI，把复核时间删掉。**结果试点时用户发现总操作量并未下降。纠偏是把复核、纠错、升级和模型等待造成的成本都纳入测量；本轮无正收益就如实报告，并找真正卡点。

## 9. 有答案自测

1. 420 小时释放等于减少多少人员？**答：**不能直接换算裁减人数。工时可能分散、技能不可互换，且岗位工资仍存在；先确认可变现机制。
2. 为客户算收益，用营业额还是毛利？**答：**与增量价值相匹配，收入增长通常应扣除新增直接成本，以可归因增量利润或贡献分析，口径让财务确认。
3. 被问不确定的产品能力，当场说“不知道”会减分吗？**答：**单纯结束会显得缺乏推进能力；“当前未确认，需什么证据、找谁、何时反馈”是负责任的推进。
4. “客户已有数仓所以不用本体”是否成立？**答：**都不能仅凭标签下结论。检查是否已解决对象身份、业务语义、关系、规则、权限与动作需求。
5. 可以把公司案例的提升比例写进建议目标吗？**答：**可明确作为待验证的参考假设并说明来源，不能写成客户保证收益；最好用客户自身基线定目标。
