> **P0：第 1—5 节，约 20 分钟；P1：第 6—9 节。**售前不必自己解决所有深层技术问题，但必须准确判断哪些能答、哪些要验证、哪些需协同。以下分工是结合 JD 和面试设计的工作方法，**不是爱化身已确认的组织制度、产品承诺或试用期考核表**。

## 1. 专业边界是“承诺可追溯”，不是“什么都不敢说”

最危险的并不是现场答不出一个术语，而是把猜测当事实、把 Demo 当产品、把当前缺口说成“一点开发就能解决”。JD 明确要求区分当前产品能力、轻量开发能力与目标态能力，并在复杂需求上协同 FDE 项目经理。这个要求本身说明：岗位期待你掌握足够广的技术判断和沟通能力，同时会使用团队，而非独立承担全部平台研发。

建议维护四类能力状态：**已核验当前产品能力、条件成立后可轻开发、需 FDE/产研评估、路线图/未知**。不能因为宣传 PDF 写了“支持”就直接归第一类。当前版本能否在目标部署方式下使用、是否有许可证限制、是否可复现、是否需要特定组件，都会影响结论。

| 类别 | 需要什么证据 | 可以怎么说 | 不应怎么说 |
|---|---|---|---|
| 已核验产品 | 版本、官方说明、演示/测试、适用条件 | “在该版本与条件下已验证 X” | “所有环境都没问题” |
| 轻量开发 | 明确接口、依赖、范围、估算、维护人 | “可通过该扩展路径实现，待按范围验证” | “半天搞定，免费顺手做” |
| 复杂待评估 | FDE/产品/研发评审、架构与排期 | “涉及部署/核心改动，评估后确认” | “研发一定会给我们做” |
| 路线图或未知 | 经授权公开的路线图或待确认单 | “当前不作为本期交付承诺” | “下个月肯定有” |

能力证明的完整句子包含：**功能 + 版本 + 环境 + 测试条件 + 已观察结果 + 未测边界**。例如：“演示服务支持请求幂等，在相同幂等键连续提交三次的教学测试中只生成一张工单；还未验证客户真实工单接口。”这句话比“我们支持企业级稳定性”具体得多。

## 2. 怎样识别“轻量开发”其实不轻

开发工作量不只由代码行数决定。一个 30 行写入脚本可能触及生产库存、跨部门权限和不可逆动作；一个较长的展示组件可能只是可撤回原型。判断时看影响范围、依赖数量、权限、数据质量、性能、持续运行与交付责任。

| 需求 | 通常可先由售前做什么 | 触发协同的条件 |
|---|---|---|
| 导入脱敏 CSV 展示对象关系 | 做样例映射和界面 | 全量数据质量、主数据冲突、持续增量同步 |
| 调用公开只读 API | 验证参数与结果 | 客户专网、认证适配、限流、授权范围不明 |
| 审批后创建沙箱工单 | 在边界内做轻量验证 | 生产写回、跨系统事务、重复与补偿责任 |
| 部署完整 Data OS | 准备依赖清单和目标场景 | 由 FDE 评估环境、容量、数据与运维 |
| 连接无人车执行任务 | 展示指令与回执概念 | 物理动作、设备安全、协议、现场责任 |
| 招聘初筛/面试评估 | 演示岗位标准和人工复核 | 涉及个人资料、实际录用决策与差异影响 |

尤其要问“谁长期维护”。轻开发形成的接口适配器，如果客户每天使用，就会有版本兼容、故障处理和责任问题。售前可以写第一版，但不应因为“是我写的”就默认由你永久承担生产值守；应交付代码、说明、限制与明确接收人。

## 3. FDE 边界：正确读取面试里的两句话

面试约 21:09，面试官以“是否签了合同”解释售前与 FDE 的主要区别，并强调签约前投入可控；约 27:48 强调售前侧价值阐述，复杂本体平台部署与数据湖仓相关工作需要 FDE；约 28:46 又说明团队会背靠背协同，售前需要 FDE、交付需要售前都可支持。

因此不能把分工机械化为“签约前禁止找 FDE”“签约后我就不管”，也不能当成全行业统一定义。对你有用的原则是：**售前主导价值与验证，复杂工程及交付方案交由相应负责人评估；关键风险应在对外承诺前被看见。**FSE 的职责、售前技术专家与技术方案专家的实际分工、资源申请入口和审批人均需入职确认，不要自行扩写缩写并假装已知。

一个建议性的分工表如下，正式以团队安排为准：

| 事项 | 售前主要贡献 | 需要谁一起确定 |
|---|---|---|
| 客户需求与成功标准 | 诊断、建模、记录证据、提出验证设计 | 销售、客户业务/IT |
| 原型与轻量 POC | 快速实现、演示、测试与边界说明 | 产品能力接口人、必要时 FDE |
| 深层集成与生产架构 | 提供场景、依赖、已验证结果 | FDE 项目经理牵引产品/研发 |
| 价格、合同与承诺 | 提供技术范围、估算假设与验收条件 | 销售/商务及相应授权人 |
| 上线与长期运行 | 交接需求与客户预期，必要时支持沟通 | 交付、运维与客户责任人 |

## 4. 发给 FDE 的应是一份可决策的问题包

不要只发“客户要数据不出域，帮忙看看”。对方还得重新做需求诊断。更好的请求是：“客户计划在专网使用环卫工单建议与审批建单，涉及巡检、合同和工单三个系统。样本读取已验证；现有不确定项是身份映射、生产写 API 的幂等机制与模型部署。附件包含数据流图、字段样例、约束、当前版本与 POC 目标。请评估可用架构、需客户补齐的条件和排期范围，本周五方案会前需要确定哪些口径可对外。”

交接包包括八件东西：一页业务问题；相关人员与决策流程；当前/目标流程；对象与数据字典；系统接口和权限；验证记录与失败样本；能力与承诺清单；待决策项及负责人。每个附件都标时间、版本、数据范围和共享权限。客户口头原话与售前解读分开，防止问题在转述中被悄悄扩大。

最重要的两张表是**已承诺表**和**未解决表**。前者记录具体句子、场合、谁确认、范围和证据；后者记录问题、对业务/排期的影响、所需证据、责任人及预计反馈时间。若销售口径和技术证据不一致，先内部对齐更正；不要等客户发现落差。

## 5. 在入职第一周建立最小工作系统

你只有五天准备，不应试图预先背完产品内部实现。入职后优先获取：可访问的产品环境、架构说明、发布日志、能力矩阵、获准展示的 Demo、典型 POC、标准问答、角色联系人和当前项目样例。拿不到某份材料就记“待获取”，不自行补成公司事实。

建议向经理核对：“我先把售前定位成需求与价值判断、三层讲解、快速演示和可控 POC；涉及完整部署、复杂集成和产品改动时，按团队机制协同。第一阶段您最希望我独立完成哪几项交付，哪些场景需要先跟访？”这比问“我是不是不够好”更容易得到可行动反馈。

工作台只需几类持续更新的记录：客户问题、能力确认、演示资产、验证结果、学习缺口。每天把一个真实客户问题转成一条可回答问答，并链接证据；每周复盘一次最大的未知如何被消除。你不必展示自己知道一切，应展示对问题的响应越来越准确和可复用。

## 6. P1：变更、例外和技术债如何留下痕迹

客户临时加“自动跨区调度”时，不应仅在聊天中答应。记录原范围、新要求、业务原因、新增数据/权限/规则、成本与排期影响、验证变化，以及谁批准。先说明它是否影响本轮目标；若会挤掉原有核心验证，就明确做取舍。

对于影响长期架构的决策，可采用简短 ADR（架构决策记录）：背景、选择、备选方案、理由、影响、状态、责任人。AWS 官方 ADR 指南强调记录决策及其背景与考虑，便于后续人员理解为什么这样做。[AWS：架构决策记录](https://docs.aws.amazon.com/prescriptive-guidance/latest/architectural-decision-records/introduction.html)

环卫例子：“本轮采用审批后沙箱建单，因为客户生产写接口尚未获准；不验证无人审批执行；代价是不能用本轮证明生产闭环。若生产接口和审批规则就绪，则由交付团队评估升级。”记录这种临时选择，可防止后续工程师把原型假设误当正式架构。

## 7. P1：把一个项目变成资产，而不是变成更多文件

资产的价值在于别人能正确复用。一个 Demo 文件夹至少要有：用途与适用对象；5 分钟启动方式；依赖与版本；数据来源/脱敏/授权说明；演示脚本；已实现与模拟项；正常及失败用例；已知限制；负责人和最近验证日期。只留截图和散乱代码，不能称为可复用资产。

行业本体也不能直接复制客户专属数据。应把通用模式与客户实例分离：通用层保留道路—责任区—班组—事件—工单关系；客户层保留具体编码、合同、SOP 和权限。若接入补货项目，可复用审批、幂等、异常队列和状态追踪模式，重新建 SKU、库存与供应链规则。跨客户复用应遵守公司的授权和保密安排，客户身份、合同信息及敏感数据不能因为“学习”就带入公开演示。

问答资产采用“问题原句 → 简明回答 → 适用条件 → 展开说明 → 证据 → 负责人/日期”。能力发生变化时更新证据和状态，而不是把旧答案永久保留为当前口径。至少在重要客户演示前检查模型、产品、第三方 API 和数据源是否有变化。

## 8. P1：三个典型失败和更好的处理

**失败：技术专家变成无上限临时研发。**售前连续两周修客户生产脚本，既没有验收也没有移交。处理：明确该任务已从原型进入持续交付，整理问题包让负责人确定维护与资源；在接手前说明期限和边界，确保业务不中断与职责可持续。

**失败：FDE 接手发现关键指标完全没定义。**客户说“演示时你们答应很准确”，售前无法拿出样本与计算方法。处理：从第一次演示就记录“展示内容”和“验证结论”的差别；正式 POC 的指标需双方确认，限制条件随结果一起交接。

**失败：销售问能否支持私有化，售前回答“能”。**交付才发现客户要求完全断网，但方案依赖云端模型和外部地图服务。处理：把“私有化”拆成应用、数据、模型、身份、日志、外部工具和更新方式；明确哪些节点出网、是否有替代能力及相关效果代价。产品提供某种部署形式，不代表所有模块在断网下等价运行。

## 9. 有答案自测与实际产出

1. 签约前 FDE 不能参与吗？**答：**面试同时强调投入可控与灵活协同。关键工程风险应在承诺前按团队机制请 FDE 评估，不能机械以合同切断协作。
2. 产品宣传说“支持”，可以写已验证吗？**答：**应记“材料声明”，核对当前版本、环境和可重复证据后才记“已验证”。
3. 不懂某项底层实现，怎样仍能推进？**答：**说明已知边界，收集影响判断的环境、输入输出和验收要求，提交具体问题包，跟进验证和对客反馈。
4. 客户要求很简单，仅需 20 行代码，是轻开发吗？**答：**还需看权限、生产影响、依赖、恢复和持续维护；行数不能决定风险与交付责任。
5. 什么资产能体现你的试用期进步？**答：**经经理认可的实际交付，例如可演示的场景、准确需求蓝图、清晰验证报告、可复用问答；这里不是公司已确认考核指标。
