## 1. 先看完整问题：客户要的结果，由哪些能力共同完成

客户问：“订单 O-1001 为什么还没发货？能不能换个仓库，明天送到？”

这句话实际包含好几个任务：

1. **理解诉求。**识别出订单编号、未发货问题、“明天送到”的目标。LLM 可以处理语言、补问缺失信息。
2. **取得事实。**查订单系统中的状态、商品数量，查仓储系统中的可用库存，查物流时效。事实来自业务系统。
3. **理解关系。**知道这个订单属于哪个客户、包含什么商品、商品在不同系统里对应哪个编码。这需要数据映射和业务模型。
4. **判断条件。**订单是否允许改仓，另一个仓能否满足数量、地址和时效。需要业务规则，部分计算需要专门的程序或模型。
5. **提出并执行方案。**先说明可选方案和代价，再按权限与流程提交变更，取得执行回执。
6. **检查结果。**改仓申请是否成功，货是否真正发出，最终是否送达。三个状态不能混为一谈。

因此，看到一个很流畅的聊天界面，还不能判断背后的方案是否成立。你需要能把这六步展开，指出每一步的依据和输出。

**掌握到这里：**能把客户的一句话拆成“理解—查事实—查关系与规则—选方案—执行—验收”。后面的术语，都放进这条链路理解。

## 2. LLM、Prompt、上下文与微调：模型知道什么，又缺什么

### LLM 是怎样产生回答的

LLM 是大语言模型。可以把它的基本过程理解为：读取当前输入，把文本处理成一串 token，再根据训练形成的能力和当前上下文，逐步生成后续内容。**Token 是模型处理文本的单位**，可能是字、词的一部分或符号，不能固定理解成“一个汉字就是一个 token”。

训练让模型获得语言、知识和一定的推理能力；本次对话里提供的资料，让它有机会围绕特定业务回答。但如果订单系统里的状态今天刚变化，模型通常不会凭空知道。

这也解释了“幻觉”：模型可能生成听起来合理、实际没有依据的内容。表达流畅和事实可靠，是需要分别验证的两件事。把随机性调低，也不能保证事实正确。

### Prompt 和上下文有什么区别

**Prompt 是你给模型的指令和输入。**例如：“根据所附报销制度回答；注明条款；缺少城市或员工级别时先询问。”

**上下文是本次模型实际能看到的信息集合。**通常包括指令、用户问题、历史消息、检索到的资料、工具返回值等。不同产品对这些词的使用范围略有重叠，工作中重点看模型到底收到了什么。

如果模型看不到最新制度，你只把“请认真、务必准确”写十遍，也没有补上事实。上下文工程做的是：把需要的信息放进来，把无关、过期、冲突的信息处理好，并保留来源。

上下文窗口有容量限制；即使资料能全部放下，模型也未必稳定找到关键条款。知识库很大时，需要检索与筛选。

### 微调适合解决什么

微调通过训练样本调整模型参数，可以用于适配表达风格、输出模式或特定任务行为。RAG 通常是在回答时检索外部资料，知识更新主要通过更新资料与索引实现。

例如，要求客服始终按“问题—证据—处理建议”的格式输出，可先验证 Prompt 和结构化输出是否够用；稳定、大量的任务需求再评估微调。要知道此刻订单是否发货，则需要查业务系统。即使做了微调，也仍然需要实时数据。

**售前怎么说：**“模型负责理解和组织信息，企业的最新事实要通过资料和业务系统提供。我们会分别验证回答能力、事实来源和执行能力。”

**掌握到这里：**能解释模型为什么会编造，知道 Prompt、补上下文、查系统和微调各自在解决什么问题。暂时不需要推导注意力公式或独立训练大模型。

## 3. RAG：企业知识问答为什么要先找证据

RAG 的全称是 Retrieval-Augmented Generation，即“检索增强生成”。核心是：**先找到与问题相关的外部信息，再让模型依据这些信息生成回答。**

### 以报销制度为例，完整走一遍

假设虚构的公司制度规定：“普通员工在上海出差，住宿上限为每晚 550 元；超标需要专项审批。”

员工问：“我去上海住一晚，600 元能直接报吗？”

系统需要完成两条链路：

**资料准备时：**

- 把 PDF、网页等解析成可读取的内容；扫描件可能先做 OCR，把图片中的文字识别出来。
- 将文档分成适合检索的片段。分段叫 chunking，不能把“适用城市”“员工级别”和“金额上限”切散得无法理解。
- 保存文件名、条款、版本、生效时间、访问权限等信息，并建立检索索引。
- 若使用向量检索，会用 embedding 模型把文本转成数字向量，以便寻找语义接近的内容。

**员工提问时：**

- 理解问题中的上海、住宿、600 元等条件；员工级别未知时，从授权资料获取或补问。
- 根据服务端确认的用户权限和制度适用时间检索条款，必要时结合关键词、向量搜索，再对候选结果重新排序。未授权的资料应在进入模型上下文前被排除。
- 把相关条款交给 LLM，让它解释：“按普通员工标准，600 元超过 550 元上限，需要专项审批”，同时标出依据。
- 找不到适用条款或存在版本冲突时，说明缺口、继续查证或转人工。

### 向量是什么，为什么能帮助检索

Embedding 可以理解为“把文本转成便于比较含义的数字表示”。“酒店费用能报多少”和“住宿报销上限”字面不同，却可能在语义上接近，因此向量检索有帮助。

但“意思接近”不等于“业务上正确”。上海和杭州的住宿条款很像，金额却可能不同；订单 O-1001 与 O-1002 只差一位，实际是两笔业务。精确编号、地区、日期、适用人群应结合关键词、过滤条件或数据库查询处理。

**重排 rerank** 是对初次找到的候选片段再判断相关性，尽量把真正适用的证据放前面。它改善候选排序，无法凭空补出知识库里没有的条款。

### 回答错了，先定位哪一步错

| 现象 | 可能原因 | 第一项检查 |
|---|---|---|
| 完全没找到住宿条款 | 文档没导入、解析失败、切段不合理 | 解析结果里有没有完整条款 |
| 引用了杭州的标准 | 条件没识别或过滤错误 | 检索结果的地区和适用范围 |
| 引用了旧金额 | 版本和生效日期没处理好 | 索引中的制度版本 |
| 条款找对了却回答错误 | 模型误读、忽略例外、指令不清 | 本次实际上下文和生成结果 |
| 普通员工查到保密文件 | 检索或下游权限控制不完整 | 服务端是否按真实用户权限筛选 |

所以，“换一个更强模型”只是可能的解决方向之一，要先找到错误发生在哪一环。

### RAG 与查数据库怎么选

“报销规则是什么”通常从制度文档获取；“我的报销单现在谁在审批”通常查业务系统；“本月已报销多少钱”通常让数据库或统计服务准确汇总。它们可以组合进同一个助手。

**售前怎么说：**“我们会让回答关联到适用的制度证据，并验证版本、权限和缺少依据时的处理。实时状态和金额统计会接对应业务系统。”

**掌握到这里：**能画出“解析与建索引—检索—把证据交给模型—回答与引用”，能区分检索错误和生成错误，并用一份小制度验证正常、例外、无答案三类问题。

## 4. API、SQL 与 Function Calling：AI 怎样查数据、办事情

### 先分清三个概念

**API 是软件提供的调用接口。**例如订单系统开放“查询订单”“提交改仓申请”两个能力，别的程序按规定提交参数，就能收到结果。

**SQL 是查询和操作关系数据库的语言。**适合按条件筛选、关联表、统计数量与金额。售前至少要能读懂一条查询在查哪张表、用了什么条件、统计口径是什么。例如“已付款订单销售额”要排除未付款，并确认退款如何扣除。

**Function Calling / Tool Calling 是模型输出结构化工具调用请求的机制。**它让模型表达“我要调用哪个能力，参数是什么”，具体执行由应用程序或工具服务完成。

API 可以被包装成工具，数据库查询也可以被包装成工具。模型并不需要直接获得数据库管理权限。

### 查询订单的一个完整往返

开发者先提供工具说明：“get_order 用订单编号查询用户有权查看的订单，参数 order_id 必填。”

用户说：“帮我看一下 O-1001。”

模型可能输出如下示意请求；这里的字段仅用于教学，并非 Agentrix 的接口格式：

```json
{
  "tool": "get_order",
  "arguments": {
    "order_id": "O-1001"
  }
}
```

接下来由后端程序执行：

1. 检查参数是否符合要求、用户是否有权查看该订单。
2. 调用订单 API 或受控数据库查询。
3. 获得业务结果，例如“已付款、待出库、更新时间 10:30”。
4. 将结果交回模型，模型再用自然语言回复用户。

==生成了工具调用请求，只表示模型提出了操作；真实执行结果要看程序返回的业务回执。==

### 查询和修改，为什么要求不同

查订单是读操作。改仓、退款、发货会改变业务状态，除了参数格式，还要检查：

- **对象与状态：**订单确实存在，并且当前状态允许变更。
- **权限：**当前用户和服务账号被允许做什么。不能只靠 Prompt 中一句“禁止越权”。
- **业务规则与审批：**例如已出库不能改仓；超过一定金额的退款需要指定角色审批。具体阈值由客户制度确定。
- **重复与超时：**提交退款后连接断了，可能退款已成功、只是回复没收到。应查询结果，并设计幂等机制，也就是让重复提交不重复产生业务结果。一种做法是使用同一业务请求标识，由服务端核对、保存处理状态并返回已有结果；还需妥善处理同时到达的重复请求。仅在前端多传一个编号并不能保证幂等，接口不支持时，超时后不能盲目重新退款。

合法 JSON 只说明内容能按这种格式解析；还要按 Schema（字段结构约定）检查必填字段、类型等要求。即使结构校验通过，金额可能错、订单可能选错、操作也可能没有授权，仍需分别验证。

### 动手时应该能读懂什么

你不必背完整接口规范，但要能看懂：请求地址与方法、身份凭证放在哪里、输入字段、输出字段、错误信息。凭证放在受保护的配置里，不能写进公开前端代码。

常见 HTTP 提示中，401 通常先查身份凭证，403 通常先查权限，429 通常表示限流。具体含义仍以接口文档和响应为准。收到 HTTP 200 后，也要检查业务字段：接口收到请求，不一定代表退款完成。

**售前怎么说：**“模型识别要查什么、提出调用参数；业务服务核验权限与条件后执行，我们根据真实回执确认结果。”

**掌握到这里：**能借助 AI 接一个只读 API，检查请求与返回，处理空结果和失败；讲得清修改操作比查询多了哪些控制。不能只展示一段‘已完成’的模型回复。

## 5. 本体、知识图谱与语义：怎样让系统理解业务里的“同一件事”

本体 Ontology 在这里可理解为一套明确的业务定义：**有什么对象、对象如何关联、字段是什么意思，以及业务允许发生什么变化。**在企业产品中，它常与事件、动作、规则一起实现；这些能力的具体边界要看产品。

### 用订单与库存建一个小模型

| 要素 | 示例 | 解决的问题 |
|---|---|---|
| 对象类型 | 客户、订单、商品、仓库、库存记录 | 业务里有哪些东西 |
| 对象实例 | 客户 C-018、订单 O-1001、商品 P-007 | 当前讨论的具体是哪一个 |
| 属性 | 订单状态、下单时间、商品数量 | 这个对象有哪些信息 |
| 关系 | 订单属于客户；订单包含商品；库存位于仓库 | 数据怎样关联起来 |
| 事件 | 订单已付款、库存被预占、商品已出库 | 什么事情在什么时候发生 |
| 规则 | 已出库不能改仓；可用库存必须足够 | 哪些条件限制业务操作 |
| 动作 | 提交改仓申请、预占库存 | 系统可以进行什么业务操作 |

例如，库存表写着“在库 10 件”，其中 8 件已被其他订单预占。本例定义“可用库存 = 在库数量 − 已预占数量”，因此可用量只有 2 件。真实企业可能还有冻结、质检、在途等库存口径，需要再明确。

如果客户要买 5 件，系统只看“10”就答应发货，会犯业务错误。**本体建模的价值之一，是让‘有库存’这样的日常用语拥有明确的业务含义。**

### 为什么把几个系统的表导入还不够

同一客户在 CRM 中叫“华新公司”，在财务系统里叫“上海华新科技有限公司”。名称相似只能提供线索，不能直接当作同一客户。需要可靠标识或经过核验的映射，才能把客户、订单、应收款关联起来。

映射还要处理冲突：一个系统的记录是否过期，同名企业是否实际不同，合并后以哪个来源的哪个字段为准。

这就是售前可以参与的建模工作：找业务负责人确认定义，列出来源和关联依据，拿真实样例检查。先用表格画清楚，已经能发现不少问题。

### 本体与知识图谱是什么关系

本体侧重业务定义与约束；知识图谱用实体及其关系组织具体知识。例如“订单 O-1001 属于客户 C-018”可以表示为一条关系。本体帮助说明这里的“订单”“客户”“属于”各是什么意思。

一个图里连了很多节点，不代表定义一致、数据正确或业务规则已经执行。数据库、图结构和应用代码可以共同承载业务模型，具体选型取决于查询、规则和维护需求。

GraphRAG 则是把图组织或图检索与生成结合的一类方法，适合评估关系关联、跨材料汇总等需求。它与本体不是同一个概念；有多表关联需求，也不意味着必须上图数据库。

**售前怎么说：**“先把订单、客户、商品和库存的定义与关系统一，AI 才能围绕同一笔业务查数据、判断条件。我们会用样例核对身份、库存口径和状态变化。”

**掌握到这里：**能为一个场景列出 5 个左右的核心对象，画关系，说明关键字段来源，写出几条业务规则。暂时无需独立实现 OWL 推理器；当涉及复杂语义推理时，再与技术团队细化。

## 6. Workflow 与 Agent：下一步由谁决定

**Workflow 是预先安排的流程。**开发者定义步骤、分支和条件，系统按这些安排运行，其中某些步骤可以调用 LLM。

例如退款申请：读取订单 → 检查退款条件 → 按金额进入对应审批 → 执行退款 → 通知结果。流程里可以让模型总结退款原因，但审批路径仍按明确规则走。使用了模型，也仍然可以是工作流。

**Agent 是围绕目标，根据当前信息和工具结果决定下一步的系统。**例如“调查这批订单为什么延迟”：它可能先查订单，发现集中在一个仓库，再查库存；库存正常，就继续查承运商记录。调查路径不一定事先完全固定。

常见运行过程是：

```text
收到目标 → 查看已有信息 → 选择下一项查询或动作
                   ↑              ↓
              继续判断 ← 获得工具结果
                   ↓
             已有结论，或转人工
```

### Agent 的自主性为什么需要边界

需要明确它能用哪些工具、最多运行多少步、花费和时限、哪些动作要人确认、什么情况必须停止。例如调查订单延误时，可以允许只读查询；改仓和退款则按业务授权另外处理。

否则可能出现：同一问题查十遍、工具失败后反复重试、为了完成目标擅自改变订单。给出一个宏大的目标，不能替代这些设计。

### 两者可以组合，多 Agent 也不是必选项

固定流程可以在某一环调用 Agent 调查原因；Agent 得到结论后，可以进入固定审批流程。

多个 Agent 适合有实际分工需求的任务，例如不同专业知识、工具权限或并行调查。代价是更多调用、协调、共享信息和错误传播，需要验证收益。两个 Agent 得出相同结论，也可能只是引用了同一个错误来源。

**售前怎么说：**“确定的审批步骤按流程执行，需要根据线索展开的分析交给 Agent。每种动作的权限、停止条件和交接方式都会写清。”

**掌握到这里：**拿一项客户任务，能标出哪些步骤固定、哪些需要模型判断、哪些要人工确认，并说明为何单 Agent 或工作流已够用，或为何确实需要协作。

深入：[[AI-05-Agent工作流MCP与Skills]]。

## 7. MCP 与 Skills：怎样接能力，怎样复用做事方法

这两个词经常一起出现，但关注点不同。

### MCP：让 AI 应用与工具服务按共同约定连接

MCP 是 Model Context Protocol。先抓住最常用的一部分：AI 应用可以通过标准方式发现工具说明、发起调用、取得结果。

例如企业封装一个订单工具服务，提供“查订单”和“查库存”。支持相应 MCP 能力的 AI 应用，可以按约定接入这个服务。服务再去调用 ERP、仓储系统的接口。

MCP 还可以承载资源和提示模板等能力，入职速学先掌握工具连接这条路径即可。支持 MCP 不代表已支持所有可选功能。

**它能减少重复接线，但客户系统仍然需要可用接口、字段映射和授权。**老系统没有开放接口时，仍要评估集成方式；协议本身不会自动打通。

### Skills：把一类任务的做法整理成可复用材料

一个“订单延迟分析” Skill 可以包含：

- 使用条件：用户询问订单延期原因或补救方案。
- 输入：订单编号、期望送达时间。
- 步骤：先查付款与出库，再查库存和物流，区分事实与估计。
- 输出模板：原因、证据、可选动作、待确认条件。
- 异常处理：数据缺失时列出缺口；涉及变更时进入相应审批。
- 可选脚本或参考材料：统计工具、业务术语说明、示例。

开放 Agent Skills 规范中常用 `SKILL.md` 描述技能，并按需附带脚本和参考资料。爱化身产品中的 Skills 如何组织、加载和执行，需要看实际产品，不能直接假定与某个开放规范完全一致。

### 放在同一个任务里看

| 概念 | 在订单案例里做什么 |
|---|---|
| Function Calling | 模型提出“调用 get_order，参数为 O-1001” |
| MCP | 为应用与工具服务提供标准连接和调用约定 |
| Skill | 告诉 Agent 如何按业务步骤分析订单延迟 |
| API | 订单系统实际提供数据或操作的接口 |

它们可以共同工作，也不要求永远全部出现。读取 Skill 通常是在本次任务中提供指导，不等于训练模型；接上 MCP 工具也不会自动获得业务权限。

**售前怎么说：**“MCP 帮助统一接入工具，Skills 帮助复用分析步骤与业务方法。落到客户环境，还要核验接口、数据字段、账号权限和执行效果。”

**掌握到这里：**能解释这四个概念的分工，写出一个简单 Skill 的输入、步骤、输出，并说明它需要哪些真实工具。暂时不用背完整协议报文。

深入：[[AI-05-Agent工作流MCP与Skills]]。

## 8. Agentrix 三层架构：把前面的能力组织成企业产品

根据公司介绍，Agentrix 按 **Data OS、Agent OS、Agent Workforce** 三层组织能力。“OS”在这里用于表达平台定位和能力组织；向客户讲时，重点讲业务分工。

继续用订单延迟案例：

| 层 | 主要回答的问题 | 在案例中承担的工作 |
|---|---|---|
| Data OS | 有哪些可信数据，它们在业务上是什么意思 | 接入订单、库存、物流与制度；关联客户和商品；提供对象、状态、规则及可追溯依据 |
| Agent OS | 如何组织任务，调用哪些能力，怎样控制过程 | 安排查订单、查库存、评估方案；组织工作流或 Agent；衔接工具、审批、运行记录与异常处理 |
| Agent Workforce | 哪个岗位用，处理什么工作，输出什么结果 | 面向客服或履约人员提供工作入口，按岗位 SOP 生成原因分析、处理建议、待办和结果反馈 |

以上是依据公司材料作的功能解释。某一步当前在哪个模块实现、是否需要项目开发，应拿实际产品验证；三层在工程上也可能共同完成一项能力。

### Data OS 为什么不只是向量知识库

向量知识库主要支持语义检索，是其中可能用到的一类能力。

企业还需要处理：订单与客户怎样对应、可用库存怎么算、哪个状态更新、谁有权查看、某条结论依据哪个系统、哪些动作被允许。Data OS 的公司定位覆盖更广的数据组织与业务语义能力，包括结构化与非结构化数据、本体和关系等。

结构化订单不一定都要转成向量；精确状态、数量与关联可以通过数据库、服务接口和语义映射取得。向量化不能自动解决“两个编码是否为同一个商品”。

### Agent OS 为什么不只是让模型连续聊天

一个任务可能经历查询、等待审批、执行、失败、恢复。应用要知道当前到了哪一步，保存必要状态，记录调用结果，并控制权限、次数和费用。

同一个“改仓”请求，如果审批还未完成，任务应处于等待状态。模型再生成一次肯定回答，不能让审批状态自动变成通过。

### Workforce 怎样体现岗位价值

“履约助手”应有明确职责：处理哪些订单异常，帮助谁，允许做什么，何时转交主管，结果按什么评价。

例如它能整理延迟原因与证据、生成改仓候选，让履约人员确认后提交申请；可以衡量调查耗时、证据正确性、处理成功率和人工接管情况。只是把聊天窗口改名“数字员工”，还没有说明这些工作机制。

**一段可以练习的产品讲解：**

> 企业的订单、库存、物流和制度分散在不同地方。Data OS 把数据组织成有业务含义的对象、关系和依据；Agent OS 协调查询、分析和受控执行；Agent Workforce 再把这些能力放进客服、履约等岗位的日常工作。我们先选一个明确场景，验证从查到原因到完成处理的整条流程。

**掌握到这里：**能用一个案例讲清三层，说明数据从哪里来、任务如何运行、岗位得到什么结果。入职后再对照平台菜单与真实 Demo，逐项确认已经产品化的能力。

依据与深入：[[爱化身介绍.pdf]]第 15—18 页、[[CO-02-Agentrix产品三层架构与能力核验]]。

## 9. 世界行为模型 WBM：从“知道当前状态”到“评估行动后果”

爱化身使用“世界行为模型”这一术语，公开材料将其与业务行为、决策、结果和反馈联系起来。现有资料可以帮助理解公司方向，但不足以确认完整内部模型架构、训练过程和效果。

**一个实用的理解问题是：在当前业务状态下，如果采取某个动作，后续可能怎样变化？**下面用通用教学设计解释，不把示例算法说成公司实现。

### 改仓为什么不能只查一个库存数字

假设本例订单需要 5 件商品，承诺明天送达：

| 候选 | 当前条件 | 采取动作后的预估 | 判断 |
|---|---|---|---|
| 保持 A 仓 | 可用库存 2 件 | 等补货后预计后天送达 | 当前不能满足目标 |
| 改为 B 仓 | 可用库存 8 件，尚未过截单时间 | 按示例物流估计明天送达，运费多 20 元 | 是候选，仍需核验和授权 |

这张表涉及几类不同知识：

- **本体与数据：**哪个商品、哪个仓、什么叫可用库存、订单当前状态。
- **规则：**订单是否允许改仓、截单时间、费用增加由谁批准。
- **预测或计算：**从 B 仓发出，预计何时送达、成本多少。
- **决策：**在时效、成本和其他订单需求之间如何选方案。
- **执行与反馈：**实际改仓、发货、签收的结果是否符合预估。

本体把事实和业务语义组织起来；预测后果还需要规则、统计、专业模型或模拟等机制。图里关联了仓库和订单，并不能直接推出准确的到达时间。

### 为什么需要结果反馈

如果 B 仓实际后天才送达，要检查偏差来自哪里：库存状态过期、出库晚、承运商异常，还是时效估计本来就偏乐观。

改进可能发生在数据更新、规则、提示词、工具或预测模型上。记录结果不等于模型已自动学会；哪些内容可以更新、如何验证和发布，需要明确管理。

公司如果展示“方案推演”或“持续优化”，你可以进一步追问一个具体样例：输入是什么、候选如何生成、预测依据是什么、如何检验实际效果。这样能把产品名词落实到能力。

**售前怎么说：**“我们关注的不仅是当前有什么数据，还包括采取行动后可能带来的影响，再通过实际结果检验和改进。具体场景需要明确规则、预测依据和验证条件。”

**掌握到这里：**能分清事实、规则、预测、建议和已执行结果；能提出验证问题。入职阶段不需要根据 WBM 名字猜测它用了强化学习或某种特定神经网络。

深入与公司来源：[[DATA-05-世界行为模型与可验证决策]]、[[数据架构来源]]。

## 10. Demo、POC 与验收：怎样证明方案值得做

**Demo 展示一条使用路径。**例如输入订单号，看到原因与建议。可以使用模拟数据，但展示时要说明哪些数据、接口和动作是真的，哪些是模拟。

**POC（概念验证）验证事先约定的可行性问题。**例如“在客户提供的订单、库存和物流数据上，能否准确查明已定义的几类延迟原因”。它需要样本、对照答案、范围与判定方法。

### 接到“做一个订单助手”时，先补齐什么

至少明确：谁使用、现在怎么处理、最费时或最易错的环节、需要哪些数据、是否允许写入、怎样算成功。

例如，可以把模糊目标收敛成：

> 客服输入订单号后，系统基于授权数据展示当前状态、可确认的延迟原因和证据；资料不足时列出缺口。本轮先验证查询与分析，改仓操作另按接口和审批条件安排验证。

这是一个可以准备数据、搭建流程和检查结果的范围。

### 验收怎么写才有用

| 验证问题 | 准备什么 | 观察什么 |
|---|---|---|
| 正常订单能否正确解释 | 已有人工核对结论的样本 | 状态、原因、证据是否对应 |
| 缺少物流记录怎么办 | 缺字段、无记录的样本 | 是否说明缺口，是否编造确定原因 |
| 未授权订单能否被查询 | 不同角色与订单归属 | 是否在系统侧正确拒绝 |
| 改仓请求超时怎么办 | 可控制失败的测试环境 | 是否查回执，是否避免重复执行 |
| 是否节省工作时间 | 现有人工流程的基线 | 包含核验、修改和接管在内的总耗时 |

样本要覆盖常见情况与关键异常。演示时选出的几条顺利案例，不能代表全量效果；业务验收标准应由项目双方结合风险和范围约定。

### 性能、成本和错误也属于方案

一次 Agent 任务可能调用模型多次，还调用检索、数据库和外部服务。因此应看**完整任务**的耗时、成功率和费用，不能只报一次模型调用有多快。

模型费用通常与输入、输出 token 等计费项有关；完整成本还包括检索、存储、工具、运行资源和人工接管。选型要用同一批业务样本比较效果、延迟、部署约束和成本，无须先背所有模型排行榜。

排错时保留这次任务的运行记录，通常称 trace：收到了什么输入、检索到什么证据、调用了哪些工具、返回什么、最后业务状态如何。它帮助把“AI 回答不对”定位成具体问题；记录内容也要遵循客户的数据与权限要求。

**掌握到这里：**能写一页 POC 范围和验收表，为正常、缺数据、越权、调用失败各准备样例，并解释 Demo 跑通与实际可交付之间还需要哪些证据。

深入：[[PRE-01-需求诊断与高层技术沟通]]、[[PRE-02-Demo工作坊与POC设计]]、[[AI-06-评测可观测性与成本性能]]。

## 11. 作为售前技术专家，到底需要懂多深

依据岗位 JD，这个角色要求客户沟通、业务建模、快速原型、API/数据处理和轻量 POC。因此，需要做到**解释机制、拆解方案、完成小验证、判断问题出在哪一环**。

| 方面 | 可以工作的应用深度 | 需要进一步协同的工作 |
|---|---|---|
| AI 概念 | 用业务例子解释 RAG、工具、Agent 的机制与选择理由 | 模型训练、大规模推理优化等深入实现 |
| 本体与数据 | 列对象关系、确认字段口径、做简单映射和 SQL 查询 | 复杂语义推理、大范围主数据治理 |
| 开发与接口 | 借助 AI 在熟悉技术栈中接接口、做界面、检查逻辑、处理基本失败 | 复杂系统集成、生产容量与高可用架构 |
| 公司产品 | 在实际产品中复现样例，明确哪些能力已验证、哪些需配置或开发 | 版本承诺、复杂能力边界由产品与技术负责人确认 |
| 售前验证 | 把需求收敛成范围、数据依赖、Demo 与验收条件 | 和销售、FDE、产品共同确定完整交付方案 |

这是一张成长与工作分工表，不能据此推断公司要求你第一天全部独立完成。入职后应拿它与主管对齐首个任务和阶段产出。

**借助 AI 写代码时，你至少要能检查四件事：**输入是什么；数据从哪里来；真正执行了什么；结果和错误如何验证。例如你不熟悉某段语法，可以请 AI 解释；但展示“已退款”之前，要知道它是否调用了真实服务、得到了什么回执。

遇到复杂问题，能提交“业务目标、样例输入、当前结果、预期结果、已查到的日志和待确认条件”，同事就能接着定位。这比笼统说“模型效果不好”更接近技术专家的工作方式。

## 12. 七道自测：试着先回答，再展开答案

这些题检验的是能否应用概念，不要求背术语原文。

<details>
<summary>1. 把制度上传后，助手仍回答旧报销标准，先怎么查？</summary>

先检查新制度是否成功解析并进入索引，旧版本是否仍参与检索，再看这次检索出的条款与模型实际收到的上下文。检索到正确条款后仍答错，才继续检查模型理解与指令。不能跳过这些步骤，直接判断模型不够强。

</details>

<details>
<summary>2. 用户问“我这笔退款到账了吗”，该让模型查退款制度吗？</summary>

到账状态应查退款或支付业务系统，并区分已申请、已受理、已退款与已到账。制度可补充预计到账时限，但不能证明某笔款项实际到账。

</details>

<details>
<summary>3. 模型输出了完整的“改仓”JSON，界面能显示“已改仓”吗？</summary>

还不能。要由程序核验对象、权限、状态及审批条件，调用业务服务，并读取真实结果。若服务只返回申请已受理，应显示“申请已受理”，继续跟踪最终状态。

</details>

<details>
<summary>4. 库存表有 10 件，订单要 5 件，为什么可能无法履约？</summary>

需要确认库存口径。如果已有 8 件被预占，本例可用量只有 2 件。还要看仓库、商品编码、质检状态、订单时间等适用条件。本体与数据建模帮助把这些定义、关系和规则说清楚。

</details>

<details>
<summary>5. 固定退款审批流程必须用多个 Agent 吗？</summary>

不必。清晰稳定的步骤可以用工作流，需要语言理解的节点再调用模型。根据线索调查复杂异常时可引入 Agent；多 Agent 要有实际分工收益，并验证增加的成本与失败点。

</details>

<details>
<summary>6. 客户说“我们支持 MCP，明天就能把所有系统打通”，还需确认什么？</summary>

确认哪些系统与工具已经实现 MCP 接入、底层 API 是否可用、字段是否匹配、账号有什么权限、网络是否连通，以及实际调用如何返回。协议兼容只解决一部分连接问题。

</details>

<details>
<summary>7. 有了订单与仓库的本体，为什么还不能保证改仓后明天送达？</summary>

本体能明确对象、关系、库存等业务含义。送达时间还取决于出库处理、截单时间、承运商和实际运输，需要计算或预测并验证。提出候选、估计送达、改仓成功、最终送达，是不同阶段的结论。

</details>

如果一道题答不出来，就回看对应一节，然后用自己的话重讲。等你能解释这七题，再用一个熟悉的场景练习迁移：把订单换成工单、仓库换成可用资源，重新确认对象、规则、工具和验收标准。城市治理可以在这一步引入，基础学习不需要先掌握环卫行业知识。
